# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A turn-based tactical soccer game. Players move pawns on a continuous pitch, plan moves/kicks/stances/sprints simultaneously each turn, then watch a tick-by-tick "autobattle" resolution. Beyond the match engine itself, a full **Career mode** now exists (saves, auto-generated 12-team leagues, season-long fixture calendars, standings, season rollover — see "Career mode" below); player career *progression* (newgens, aging, retirement, form) is still long-term scope, not yet built.

## Commands

Run from the repo root unless noted:

```bash
npm run dev              # starts backend (port 3001) and frontend (Vite, port 5173/5174) together
npm run dev --prefix backend   # backend only (tsx watch)
npm run dev --prefix frontend  # frontend only (vite)
```

Frontend (`frontend/`):
```bash
npx tsc --noEmit -p tsconfig.app.json   # type-check the app code — run this after any change
npm run build                            # tsc -b && vite build
npm run lint                             # oxlint
```

Backend (`backend/`):
```bash
npx tsc --noEmit    # type-check
npm run build       # compiles to dist/
```

**There is no automated test suite.** To verify logic in `frontend/src/game/*.ts` (which is plain TS with no React/DOM dependency), write a throwaway script that imports the function under test, run it with `npx tsx some-script.ts` from `frontend/`, then delete the script — this has been the established pattern for validating the resolution engine (see git history for examples: collision fuzz-testing, contest win-rate checks, kick trajectory/aim-spread checks, cooldown-bookkeeping checks, etc.).

## Architecture

### Two independent processes, no shared build

`backend/` and `frontend/` are separate npm packages with no workspace linking; the root `package.json` only wires them together via `concurrently` for local dev. There is no shared-types package — `frontend/src/game/types.ts` (`PlayerDTO`, `TeamDTO`) duplicates the shape of what the backend returns and must be kept in sync by hand.

### Backend: Express + `node:sqlite`

- Persistence uses Node's **built-in** `node:sqlite` module (`DatabaseSync`), not `better-sqlite3`. This was a deliberate choice after `better-sqlite3` failed to install on this Windows machine (no prebuilt binary for the installed Node version, and no Python/build tools for a native compile). Do not reintroduce a native-addon DB driver without checking the environment first.
- `backend/src/db.ts` opens/creates `data/game.db` and defines the schema: `teams`/`players` (the original core tables — seeds two unscoped demo teams, "Eagle FC"/"Rival United", 6-player squads each, if the DB is empty; still what the non-career match flows — hotseat/AI/solo sandbox — fetch via the unscoped `GET /api/teams`), plus the **career-mode tables** added on top: `saves` (a career's top-level container — `name`, `season` counter, `user_team_id` nullable until the player picks a team), `transfers` (always team-to-team, logs player moves — see the table's own comment for why there's no free-agent pool), `leagues` (`save_id` NOT NULL — a **new row per season**, not a mutated one; see "Career mode" below for why), `league_teams` (join table), `fixtures` (`home_score`/`away_score` nullable until played; standings are always computed live from these, never stored, so they can't drift out of sync), `fixture_goals` (one row per identified goal in a fixture the player actually played interactively — see `resolve.ts`'s `GoalScorer` below — never populated for a quick-simmed fixture), `team_tactics`, `team_corner_presets`, and `team_lineups` (one row per team, at most, in all three cases — a team with no row just plays under sensible defaults, so none of the three needed any backfill migration for already-existing teams; see "Career mode" below), and `managers` (`save_id` FK, a name/style plus the same 9 tactical columns `team_tactics` has — see "Manager system" under Career mode below for why a manager *owns* a profile rather than a team owning it directly). `teams` also grew a nullable `manager_id` column (`ensureColumn`, FK to `managers`) — null only for the human's own team, see below. Players have seven numeric attributes: `pace`, `stamina`, `skill`, `jumping`, `shot_stopping`, `reflexes` (the latter two mainly relevant to goalkeepers, see below), `heading` (redirect precision on a won header).
- **Schema changes must include a migration**, not just an edit to the `CREATE TABLE IF NOT EXISTS` DDL — that statement is a no-op against a DB that already exists on disk (this project's local dev DB persists across sessions and isn't reseeded), so a new column needs an explicit, idempotent `ALTER TABLE`. The established pattern is `ensureColumn(table, column, ddl)`: check `PRAGMA table_info(table)` for the column, `ALTER TABLE ... ADD COLUMN ...` if missing, called unconditionally on every startup so it's a safe no-op once the column exists. SQLite backfills existing rows to the column's `DEFAULT` automatically. A brand *new* table needs no such migration at all — `CREATE TABLE IF NOT EXISTS` already handles that correctly on its own — which is why `fixture_goals`/`team_tactics`/`team_corner_presets`/`team_lineups` above could all just be added directly.
- `backend/src/index.ts` is an Express layer with real write endpoints now, not just the original read-only `GET /api/teams`/`GET /api/teams/:id/players`/`GET /api/health`. Career-mode routes: `POST/GET/DELETE /api/saves`, `PATCH /api/saves/:id` (sets `user_team_id`), `GET/POST /api/saves/:id/teams`, `PATCH/DELETE /api/teams/:id`, `POST /api/teams/:id/players`, `PATCH/DELETE /api/players/:id`, `POST /api/players/:id/transfer` + its GET history routes, `POST/GET/DELETE /api/saves/:id/leagues`, `GET/POST/DELETE /api/leagues/:id/teams`, `POST /api/leagues/:id/generate-fixtures`, `GET /api/leagues/:id/fixtures`, `PATCH /api/fixtures/:id` (records a result, optionally with `scorer_player_ids`), `GET /api/leagues/:id/standings` (computed live, see above), `GET /api/leagues/:id/top-scorers` (also computed live, joined off `fixture_goals`), `POST /api/leagues/:id/simulate-round`, `POST /api/saves/:id/advance-season` (the latter two are Career mode's core season-progression mechanism, and `advance-season`'s response now also carries `firings` — see "Manager system" below), `GET/PUT /api/teams/:id/tactics`, `GET/PUT /api/teams/:id/corner-preset`, `GET/PUT /api/teams/:id/lineup`, `GET /api/saves/:id/managers` — see "Career mode" below for all of these. No auth (single-player, local-only).

### Frontend: the match engine is decoupled from rendering

All match-simulation logic lives in `frontend/src/game/*.ts` as plain, framework-free functions/types with **no dependency on React or Phaser**. `frontend/src/components/Game.tsx` owns all state (pawns, ball, score, turn, camera, selection) and orchestrates it; rendering is delegated to a Phaser 3 scene (see below), not JSX.

- **`constants.ts`** — every tunable game parameter. Tune gameplay feel here, not by scattering magic numbers. Pitch is `GRID_COLS x GRID_ROWS` (60x40 world units — real distances, not literal grid cells; the "GRID_"/"_CELLS" naming predates continuous movement and was kept to avoid a pure renaming churn). Movement/ball speed (`PAWN_SPEED_PER_TICK`, `BALL_SPEED`, `MOVE_RANGE` ticks/turn, `KICK_RANGE`) are all deliberately tuned so a turn covers a modest fraction of the pitch — an earlier pass scaled everything up proportionally with the pitch size and it felt cramped despite the bigger world, so movement/interaction radii were pulled back down independent of pitch dimensions. Interaction radii (`CAPTURE_RADIUS`, `TACKLE_RADIUS`, `REACT_RADIUS`, `PRESSURE_RADIUS`) are kept at a real "personal space" scale for the same reason — `PAWN_OVERLAP_RADIUS` is the one exception, deliberately tiny (see "Player-driven tackling and collision rework" below). Matches have no turn cap (`TOTAL_TURNS` was removed — they're open-ended). Loft/height constants (`LOFT_APEX_MIN/MAX`, `BALL_REACH_HEIGHT`) and goalkeeper constants (`GK_*`, prefixed to group them) are also here — see "Ball height" and "Goalkeeper" below. `PAWN_MOVE_BUDGET` is a pawn's fixed WHOLE-TURN distance budget (unchanged by multi-step planning); `STAMINA_CHARGES_BASE`/`STAMINA_PER_BONUS_CHARGE`/`KICK_CHARGE_COST` govern how that same budget gets subdivided into waypoints/kicks — see "Multi-step planning and stamina" below.
- **`formations.ts`** — formation *data*: `Formation`/`FormationSlot` types and `FORMATION_6V6_DEFAULT` (the same 6 GK/DEF/DEF/MID/MID/FWD positions the game has always used, now expressed as data instead of hardcoded slot constants). Adding a new squad size/shape (a future 11v11 formation, an alternate 6v6 shape) means adding a new `Formation` value here, not touching the placement algorithm. Also `LineupSlot` (a `FormationSlot` pinned to a specific `playerId`, not just a position category) — see Career mode's "Base lineup / formation" bullet below for what actually produces/consumes these.
- **`formation.ts`** — `buildFormation(players, side, formation = FORMATION_6V6_DEFAULT)`: a generic `assignSlots` algorithm with zero knowledge of squad size or shape, constructing fresh `Pawn`s (all planning/stance/cooldown fields reset) for exactly `formation.slots.length` players. **Iterates over the formation's SLOTS, not the roster's players** — for each slot, take the first remaining player matching that slot's `position`, falling back to whichever player is left if none match (a roster missing a GK entirely still fields someone in goal). Any roster players beyond what the formation needs are simply never assigned a slot and never become a pawn — correctly benched. This was a real, previously-shipped bug: an earlier version looped over *players* instead of slots, which worked fine for a 6-player roster (1:1 with the 6-slot default formation) but silently broke the moment Career mode's 12-player rosters (2 GK, 4 DEF, 4 MID, 2 FWD — see "Career mode" below) started flowing through it — the 6 real slots filled first (sometimes with the *wrong* position, e.g. a second GK cascading into a DEF slot), then every remaining player fell back to one shared hardcoded center-pitch coordinate, producing a visibly broken formation (both squads piled at midfield, a phantom second goalkeeper standing outfield). Fixed and verified via the throwaway-script pattern (a 12-player roster in the exact 2/4/4/2 shape now yields exactly 6 pawns, one per position, no coordinate collisions). Built specifically to unblock a future 11v11 upgrade without engine changes — `resolve.ts`/`contest.ts` already operate generically on pawn arrays with no squad-size assumption baked in; this was the one real hardcoded blocker. Also exports `buildFormationFromLineup(players, side, startingPlayerIds, savedSlots)` — like `buildFormation`, but seeded from a team's saved base lineup (specific players pinned to specific spots) instead of a generic position-shaped `Formation`; see Career mode's "Base lineup / formation" bullet below for the full reconciliation logic (kept slots vs. vacated slots vs. match-day newcomers) and its fallback to plain `buildFormation` on any mismatch.
- **`resolve.ts`** — the core simulation, `resolveTurn(pawns, ball): { snapshots, goal, scorer, deadBall }`. This is the most important file to understand before making mechanical changes. Pure function, no side effects, fully unit-testable via the tsx-script pattern above. See "How a turn resolves" below. Also exports `chargesFor(player)` (stamina → charge count) — see "Multi-step planning and stamina" below for how this, alongside the internal `startFlight`/`clampStepsToBudget`/`ticksForSteps` helpers, replaces the old single-`plannedPos`-or-`plannedKick` model. `GoalScorer` (`{ side, pawnId, playerId, playerName }`) is computed at each of the three places a goal can actually happen — a kicked flight crossing the line (`flight.kickerId`), a loose/deflected roll crossing it (`roll.excludeId`, the pawn whose touch produced the roll — genuinely `null` when nobody's touch is on record, e.g. an unopposed kick's landing that just kept rolling in), and a dribbled-in goal (the live `currentCarrierId`) — `scorer` is `null` whenever `goal` is null, or rarely when a goal happened with no specific touch on record. `Game.tsx` accumulates these into `match.scorers` across the whole match (mirroring how `match.events` already does) and reports them to `onCareerMatchEnd` — see "Career mode" below for where they end up persisted.
- **`contest.ts`** — every skill-check in the game funnels through `resolveContestDetailed(contestants, kind)`, where `kind` is `"loose_ball" | "interception" | "tackle" | "gk_claim" | "save" | "header"`, each with its own attribute-weight table (a `Partial<Record<attribute, number>>` — generalized beyond a fixed `{skill,pace,stamina}` shape once goalkeeper attributes needed weighting too) plus random noise. Returns a winner and a "margin" (how decisive the win was — a big margin is a clean win, a small one produces a scrappy/contested outcome instead of a clean turnover). `stanceBonus()` layers a small additional attribute-weighted term on top for pawns with an active stance (see below) — every bonus is a factor times a real `pawn.player` attribute, not a flat number, so it automatically tracks whatever new attributes get added later. `reachFactor()`/`rollSaveAttempt()` are a *different* pattern purpose-built for the goalkeeper's `jumping` attribute — deliberately not a `stanceBonus`-style additive term (an additive bonus scaling with shot distance would let a maxed-jumping keeper dominate every save regardless of distance); instead `jumping` widens the range over which `shot_stopping`/`reflexes` stay at full effectiveness, falling off toward a floor beyond it. Follow this same "gate, don't add" shape for any future attribute whose real-world effect is "helps you reach the play" rather than "makes you better once you're there." `jumping` plays a *different*, valid role in `WEIGHTS.header` (a direct additive weight) — the same attribute can be gate-only in one contest kind and additive in another; that's a property of the contest, not the attribute. `rollHeaderAttempt(pawn)` is a raw single-pawn roll (not a 2-way contest) used for an uncontested header's own difficulty check — see "Heading" below.
- **`restartSetup.ts`** — `resolveSetupTurn(pawns, deadBallSpot): ResolveSnapshot[]`, a small, dedicated pure function for the "extended setup" turns a dead-ball restart can trigger — see "Dead-ball restarts and fouls" below. Deliberately *not* a mode of `resolveTurn`: there's no live ball during setup (no kicks/captures/tackles/saves possible), so it only needs a fraction of `resolveTurn`'s machinery (movement + man-mark's auto-aim, with a simplified sequential collision pass instead of the simultaneous fixed-point Rules 1-3, since there's no contest at stake while pawns are just getting organized).
- **`aim.ts`** — `landingSpread(distance, skill, kind, onTarget?)`/`sampleLanding(...)`: a kick's actual landing point is sampled from a Gaussian spread around the aim point (a "mortar" reticle — most kicks land close, a few land meaningfully off), tighter for a shorter/more-skilled kick, wider still for a cross, tighter again for a shot genuinely lined up on goal (see "Shooting, Passing, and Crossing" below). This is what `resolve.ts`'s kick flight aims at, not the raw clicked point. Height (see below) is orthogonal to this — it doesn't affect where a kick lands, only how it gets there. Also exports `riskLabel(sigma)` (moved here from the now-deleted `kickIntent.ts` — a plain-language `"Safe"/"Risky"/"Very risky"` readout, a pure derivative of this same sigma) and the two breakpoints it's built from, `RISK_SAFE_SIGMA`/`RISK_VERY_RISKY_SIGMA`, exported specifically so `ai.ts`'s own risk-tolerance evaluation reads from the same numbers rather than a second, driftable copy.
- **`reactions.ts`** — `attemptsReaction(pawn, kind)`: a one-shot, attribute-gated chance (currently only `"press_loose_ball"`) that lets a pawn abandon its planned move to chase a ball that's just become loose nearby. Rolled once per pawn per loose-ball episode, not every tick, so a pawn's reaction doesn't flicker on and off.
- **`ai.ts`** — the AI opponent, now fully overhauled to use every system below (multi-step chains, stances, sprint, shot/pass/cross, headers) — see "AI opponent" below for the full writeup. **`tacticalProfile.ts`** — the `TacticalProfile` type + `DEFAULT_TACTICAL_PROFILE` the AI's tactical judgment is parameterized by, kept in its own file specifically so alternate profiles could be constructed without importing any of `ai.ts`'s decision logic — which is exactly what Career mode's `team_tactics` table now does for real (see "Career mode" below); this file's own type/logic needed zero changes to support that, confirming the seam was built correctly the first time.
- **`iso.ts`** — pure isometric projection math (`createProjector(rotationDeg, tiltDeg)`), used only by the Phaser scene for positioning **and** for recovering a click's world position (`fromIso`, the algebraic inverse of `toIso`) — there is no per-cell click grid anymore (see Rendering below). An extra `OOB_CELLS`-wide out-of-bounds apron is walkable on all four sides, and the goal net pocket (`GOAL_NET_DEPTH` beyond the goal line) is where scoring actually happens. Composing a world-space rotation with a fixed "diamond" shear-and-scale is still a **linear** map regardless of rotation angle — a rectangle always projects to a parallelogram, never a true non-parallel trapezoid, though the *amount* of skew visibly varies with rotation angle (inherent to combining a tilted, non-top-down camera with free 360° yaw — not a bug).
- **`api.ts`** — thin `fetch` wrappers for the non-career backend endpoints (`fetchTeams`, `fetchTeam`, `fetchPlayers`). **`careerApi.ts`**/**`careerTypes.ts`** are the separate, much larger set of wrappers/DTOs (`SaveDTO`, `LeagueDTO`, `FixtureDTO`, `StandingRow`, `TransferDTO`) for every career-mode endpoint listed in the Backend section above — kept apart from `api.ts` since it's a distinct, much bigger group of shapes, not because the underlying fetch pattern differs. Every career wrapper is called as `.then(json<T>)` with an explicit type argument (`json<T>(res)` throws a real `Error` with the backend's `{ error: string }` message on a non-OK response) since TypeScript can't infer `json`'s generic from `.then(json)` alone — there's no argument position for `T` to flow from.
- **`types.ts`** — `Pawn.plannedSteps: PlannedStep[]` is this turn's whole plan — an ordered chain of waypoints and/or kicks (see "Multi-step planning and stamina" below), replacing the old single `plannedPos`/`plannedKick`/`plannedKickLoft` fields entirely. A `PlannedStep` is `{ pos: Vec2; kick?: { loft: boolean; kind: "shot" | "pass" | "cross" } }` (see "Shooting, Passing, and Crossing" below for `kind`) — `pos` means "walk here" for an ordinary step, or "aim here" (no walking) for a kick step. Additive per-turn fields `stance` (a defensive order, see below) and `plannedSprint` sit alongside `plannedSteps`; `sprintCooldown` is the one field that is **not** turn-scoped — it persists and decrements across turns (see "Stances and Sprint" below). `PlayerDTO` carries seven numeric attributes: `pace`, `stamina`, `skill`, `jumping`, `shot_stopping`, `reflexes`, `heading` — `stamina` now also drives `chargesFor` (how many steps a turn's plan can have), on top of its long-standing role as a contest-roll factor; `heading` governs redirect precision on a won header (see "Heading" below), distinct from `jumping`'s role in winning the header contest itself.

### Rendering: Phaser 3, bridged to React

The pitch/pawns/ball are drawn by a **Phaser 3** (`phaser@3.90.0`, pinned — not the newer Phaser 4 that npm resolves to by default) scene, not SVG/JSX.

- **`frontend/src/phaser/PhaserGame.tsx`** — React wrapper that creates/destroys the `Phaser.Game` instance in a `<div>` on mount/unmount and forwards the ready scene via a callback prop.
- **`frontend/src/phaser/MatchScene.ts`** — the actual renderer. `preload()` loads the sprite PNGs from `frontend/public/sprites/`; `create()` builds static field Graphics and **one static full-world hit `Zone`** (not a per-cell grid — clicks are resolved to a continuous world point via `iso.ts`'s `fromIso`, then Game.tsx checks Euclidean distance against the selected pawn's move/kick budget). `syncState(state)` is the single entry point React calls after every render — it applies camera zoom/pan (`applyCamera`, clamped so panning can't lose the world off-screen, with more pan room available the more zoomed-in the camera is), re-projects and moves/tweens pawn and ball sprites, redraws the field when camera rotation/tilt changed, updates the reach-area highlight, the pawn/ball influence-radius debug overlay, and the planned-move/kick/stance overlay. Pawn/ball position changes are animated via `this.tweens.add(...)` (350ms linear) rather than CSS transitions.
- **`frontend/src/phaser/EventBus.ts`** — a `Phaser.Events.EventEmitter` singleton (same pattern as the official `phaserjs/template-react`), used only for the scene to announce `"current-scene-ready"`.
- **Data flow is one-directional and imperative, not prop-driven**: `Game.tsx` keeps a `sceneRef` (set once via the ready callback) and calls `sceneRef.current?.syncState(...)` in a dependency-free `useEffect` that reruns after every render, gated by a `sceneReady` **state** flag (a ref alone wouldn't trigger the effect that populates the first sprites). Click input flows the other way: the field zone and pawn `pointerdown` handlers call `this.callbacks.onFieldClick/onPawnClick`, which `Game.tsx` wires to always-fresh closures via a `handlersRef` (avoids stale `pawns`/`selectedId` in the one-time `setCallbacks` call).
- **Camera rotation/tilt/pan are not Phaser camera features** — Phaser's `camera.rotation` just spins the 2D view, which isn't what an orbiting isometric camera needs. Rotation/tilt are handled entirely by `iso.ts`'s projection math (recomputed and re-applied to every sprite in `syncState`); only **zoom** and **pan** (via `centerOn`) use Phaser's real camera. Mouse drag-to-orbit (middle/side button, horizontal = rotate, vertical = tilt), **left-click-drag-to-pan**, wheel-to-zoom, and **WASD-to-pan/Q-E-to-rotate** are all handled in `Game.tsx`, not inside the Phaser scene — see "Camera, input, and HUD polish" below for the click-vs-drag plumbing left-click panning required in `MatchScene.ts` too.
- **The camera's pan is tracked as a world-space focus point (`camera.focusX/focusY`, grid coordinates), not a raw view-space pixel offset.** This was a deliberate fix: `MatchScene`'s projection always keeps the *pitch's own* center pinned to the same view-space point regardless of rotation, so a fixed view-space pan offset stopped meaning the same physical location the instant you rotated while panned — the world would visibly swing around the pitch's fixed center instead of around wherever the camera was actually looking. `applyCamera` now re-projects `focusX/focusY` through *whatever the current rotation/tilt is* every call (`this.projector.toIso(camera.focusX, camera.focusY)`), so a rotate/tilt keeps that same world point centered. WASD's per-frame delta is still computed in view-space (that's what keeps a key's direction meaning the same thing on screen regardless of rotation — press W, the view moves up, always), but the *result* is immediately converted back to a world point via the current projector's `fromIso` before being stored, rather than staying a raw pixel offset. If you touch camera code, preserve this: never store camera position as a bare view-space offset that outlives a single frame.
- **Scale mode is `Phaser.Scale.RESIZE`, not `FIT`** — the canvas's real pixel resolution always matches its container exactly. `iso.ts`'s `VIEW_W`/`VIEW_H` remain the fixed *world* size the isometric projection targets; `MatchScene.handleResize` computes `fitZoom = min(canvasW/VIEW_W, canvasH/VIEW_H)` and `applyCamera` applies it times the user's zoom, so the fixed-size world is scaled/centered to fill whatever container size Phaser reports. `PhaserGame.tsx` runs its own `ResizeObserver` on the container div and calls `game.scale.resize(width, height)` directly, since Phaser's `RESIZE` mode only reacts to the *window* `resize` event on its own (not a parent container changing size for other reasons, e.g. entering Fullscreen).
- **Phaser's game config sets `input: { windowEvents: false }`.** Phaser defaults to `true` — it also listens on `window`, not just its own canvas, specifically so a drag-release outside the canvas still registers. That default is a trap for a canvas embedded under HTML UI: a click that starts *and ends* entirely on an HTML button floating over the canvas (e.g. an action-panel button in the HUD) still bubbles to Phaser's window listener, which projects the click's screen position into pitch coordinates and fires a field click regardless of what was actually clicked — a button could silently double as "place a kick target here." Nothing in this game needs off-canvas drag-release detection (camera orbit is handled entirely by `Game.tsx`'s own mouse handlers, not Phaser's input), so this is a pure fix with no functional loss. Don't remove it without designing around this failure mode first.
- **Ball height** (see "Ball height and loft" below) drives the ball sprite's screen-Y lift and the shadow's scale/alpha in `updateBall()`, plus an optional numeric height label — mirrors the flat pixel lift pawns already get (`TOKEN_RISE`-style), just computed live instead of constant. All of the kick-preview overlay's line widths, dot radii, and text scale (`updateOverlay()`) are divided by `this.cameras.main.zoom` — Graphics/Text objects live in world space and get shrunk right along with the pitch as the camera zooms out (and the *default*, unzoomed view is already well under 1x zoom, since the fixed isometric world is far larger in world-pixels than the canvas it's fit into), so a fixed pixel width/font-size becomes illegibly thin/tiny unless explicitly counter-scaled this way. Apply the same `/ zoom` treatment to any new on-canvas text or thin lines.
- Sprite art in `frontend/public/sprites/` (`player_home.png`, `player_away.png`, `player_gk.png`, `ball.png`) is AI-generated, stylized pixel-art, cropped tight to content and alpha-cleaned via one-off PowerShell/System.Drawing scripts (not checked in). Two things to check before dropping in regenerated art: (1) **the character's pose must have both feet flat and grounded** — a mid-stride/walking pose with a raised foot causes an unfixable-by-rendering "floating pawn" look; (2) some AI tools export a "transparent" background that's actually a semi-transparent gradient (partial alpha, not 0) — check the alpha histogram before assuming a plain crop is enough. `MatchScene.ts`'s `SPRITE_WIDTH` is `SPRITE_HEIGHT * <aspect ratio>` — recompute that multiplier to match new art's actual width:height ratio. The pitch's ground is **not** an image — it's a per-tile checkerboard fill plus deterministic speckle noise, computed directly from each tile's own projected corners in `redrawField()` (tile size is `CHECKER_CELL_SIZE`, decoupled from gameplay units so draw cost stays bounded on the larger pitch), which can't drift out of sync with the field under rotation.

### Fullscreen HUD

`Game.tsx` renders a fixed five-zone HUD (`game.css`'s `.hud-top-left/center/right`, `.hud-bottom-left/right`) that overlays the pitch in fullscreen (`position: absolute` on `.hud`, `pointer-events: none` on the shell with `auto` restored on each populated panel, so clicks pass through empty space to the pitch beneath): selected-pawn info top-left, the scoreboard genuinely centered top-center (CSS grid `1fr auto 1fr`, not flex — centering has to be independent of how wide the other two panels are), Continue/menu controls top-right, a scrollable event log bottom-left, and the action panel (Move/Kick/Ground-Loft/Shot-Pass-Cross/Stance-dropdown/Sprint) bottom-right. Windowed (non-fullscreen) mode reuses the identical JSX/CSS classes in normal document flow rather than a separate layout — the fullscreen case is the one that actually matters (this is a fullscreen-first game meant to eventually run outside a browser tab), so don't spend design effort on the windowed arrangement beyond "doesn't break."

### Camera, input, and HUD polish

The first concrete work of the confirmed "balancing + UI improvements" phase — small, mechanically-independent input/UI fixes, nothing touching `resolve.ts`.

- **Camera**: Q/E now rotate the camera (`ROTATE_KEY_SPEED` degrees/sec in `Game.tsx`, the same held-key/animation-frame loop WASD panning already used) — a keyboard alternative to the middle/side-mouse-button drag, since not every mouse has those buttons. Holding the **left** mouse button and dragging now pans the camera too ("grab the field and move it"), tracked the same way the pre-existing rotate-drag is (a `panState` ref recording the drag's start position/focus, converted to a world-space focus point via `iso.ts`'s projector — fully respecting the "camera focus is world-space, not view-space" invariant documented above). The drag reads Phaser's *actual* current zoom (`sceneRef.current.cameras.main.zoom`, i.e. `fitZoom * user zoom`) to convert screen-pixel deltas into view-space units, which is what makes the pan track the cursor 1:1 regardless of zoom level.
- **Left-click-drag panning needed pawn/field clicks to stop firing on `pointerdown`** — otherwise the very first pixel of a pan-drag would already have planted a waypoint/kick at the drag's starting point before any drag was even detected. `MatchScene.ts` now defers: a left-button `pointerdown` over a pawn or the field only records a `pendingClick` (`{type:"pawn", id}` or `{type:"field", point}`); a scene-wide `pointerup` listener fires it, but only if `pointer.getDistance()` (Phaser's own down-to-up travel distance) stayed under `CLICK_DRAG_THRESHOLD` (6px) — otherwise it's a drag, and the pending click is silently dropped instead of firing at the drag's starting point.
- **That left-button gate fixed a real, separate bug**: right-click used to *also* reach these same `pointerdown` handlers (Phaser doesn't filter by button on its own), so right-clicking a pawn or the field was firing a select/move/kick action *at the same time* as `Game.tsx`'s own `onContextMenu`-driven undo/deselect handler — the two were fighting each other, which is what made right-click "not work." Both the fieldZone and pawn-container `pointerdown` handlers now check `pointer.leftButtonDown()` before recording anything, so right-click only ever reaches `handleViewportContextMenu`.
- **Deselecting a pawn now has three distinct paths, each answering a different, separately-confirmed complaint — don't collapse these back into one without checking why they're separate**: right-click still undoes the last planned step first, only deselecting once the plan is already empty (`handleViewportContextMenu`, unchanged from its original design) — a first attempt at "right-click always deselects instantly, no undo" was tried and reverted, because it made right-click feel like it "wasn't working" whenever a chain was already queued (the instant deselect discarded the whole plan in one click, which was worse than the undo-first behavior it replaced). **Escape is the separate instant, unconditional full deselect** (`deselectPawn()`, dispatched through `keyActionsRef` — the same mount-once-listener-stays-fresh pattern `handlersRef` already established for Phaser's callbacks, needed here because the keydown listener attaches once but has to keep reading the latest `selectedPawn`/`match.resolving`). Escape will always *also* exit fullscreen — an unavoidable browser behavior for the Fullscreen API that no amount of `preventDefault` can stop — and the user is aware and fine with that for now; noted here so it isn't "fixed" by accident later. **A field click once the pawn's whole move/kick budget is spent (`chargesRemaining <= 0 || distanceRemaining <= 0`) now also deselects** (`handleFieldClick`), instead of being a silent no-op that left the pawn stuck selected — this was the actual middle ground wanted: spend the turn, click elsewhere, move on, without reaching for right-click or Escape at all.
- **The Fullscreen toggle button stays visible in fullscreen now** (`fullscreen-toggle-btn` class — deliberately *not* `hud-menu-btn`, which still hides the "← Menu" button in fullscreen, unchanged) — small and low-opacity (`game.css`), brightening on hover. Directly motivated by the Escape/fullscreen point above: since Escape can't be dedicated purely to deselect without also dropping fullscreen, this button is the actual way to leave fullscreen without relying on Escape — matters more once this ships outside a browser tab, where "Escape always quits fullscreen" is even less negotiable.
- **Fullscreen state/toggle is owned by `App.tsx`, not `Game.tsx`.** It used to be local to `Game.tsx` (a `wrapperRef`-targeted `requestFullscreen()`), which meant fullscreen silently dropped the instant you navigated away from a match — the browser auto-exits fullscreen the moment its target element unmounts, and React swaps out `Game.tsx`'s whole wrapper `<div>` on every screen change. `App.tsx` now owns `isFullscreen`/`toggleFullscreen` (targeting `document.documentElement`, not any one screen's div) and threads them down as required props to `MainMenu`, `Career` (which forwards them to its own internal `<Game>` match screen), and `Game` directly — so entering fullscreen from the main menu survives all the way through Career → Club Home → an actual match. `MainMenu.tsx` has its own small "Fullscreen" button (`menu.css`'s `.menu-fullscreen-btn`, top-right corner, low-opacity like the in-match one) specifically so the player can go fullscreen before ever starting anything, matching the fullscreen-first intent noted above.
- **`game.css`'s fullscreen layout rules key off a plain CSS class (`.game-wrapper.is-fullscreen`), not the `:fullscreen` pseudo-class** — this was a real, previously-shipped regression from the `App.tsx` move above: `.game-wrapper` is a plain descendant `<div>`, never itself the element passed to `requestFullscreen()` (that's `document.documentElement`), so `:fullscreen` — which only matches the actual fullscreen element, not its descendants — never matched `.game-wrapper` once fullscreen ownership moved off `Game.tsx`'s own wrapper. Every fullscreen-only rule (the pitch filling the screen, the HUD becoming an absolute overlay, hiding the hint text, etc.) silently stopped applying: the browser genuinely entered fullscreen, but the page kept rendering at its normal windowed size/layout inside that larger viewport, leaving a small pitch surrounded by empty space (with a page scrollbar, since normal-flow content still overflowed a viewport it wasn't sized to fill). Fixed by toggling a `.is-fullscreen` class off the already-correct `isFullscreen` prop (`className={\`game-wrapper ${isFullscreen ? "is-fullscreen" : ""}\`}`) instead of relying on the CSS pseudo-class to somehow reach a non-fullscreen-element descendant — ties the visual state directly to the same React state the `fullscreenchange` listener already keeps in sync, rather than depending on `:fullscreen`'s exact element-matching semantics. If you ever retarget `requestFullscreen()` at a different element again, remember this class-based approach doesn't care which element is literally fullscreen — it only cares what `isFullscreen` says.
- **The event log (`match.events`) now accumulates for the whole match instead of resetting every turn** — `resolveWithPawns` no longer clears it at the start of a turn; it prefixes a plain `Turn N` divider line (`eventClass` styles it as `event-turn-marker`) onto the existing history instead of a fresh array. `game.css`'s `.events-log` grew from a 160px to 240px max-height accordingly, and a new `eventsLogRef`-driven effect scrolls it to the bottom on every `match.events` change, so the newest line is always in view without the player scrolling manually. Deliberately left unbounded (no cap/virtualization) for now — matches have no turn cap (see `constants.ts`'s removed `TOTAL_TURNS`), so a very long match will grow this array indefinitely; revisit only if that becomes a real problem, not preemptively.

### How a turn resolves (`resolveTurn`)

Ball and pawns both move through continuous (fractional) coordinate space, not grid cells. A turn's tick count is `max(MOVE_RANGE, ticksForSteps(...))` across every pawn's plan (see "Multi-step planning and stamina" below) — `MOVE_RANGE` ticks is the floor for an ordinary turn, but a pawn chaining several waypoints needs proportionally more ticks to actually walk the whole plan, and everyone else just keeps ticking alongside them (idling once their own, shorter plan is done).

1. **Kick check, now per-step rather than per-turn**: there's no more up-front "whoever starts the turn within `CAPTURE_RADIUS` carries it, resolve their kick before the loop" — a kick is just one possible kind of step in a pawn's `plannedSteps` chain (see below), and it fires at whatever point in the sequence the pawn actually reaches it. When a pawn's step cursor lands on a kick step (at the very top of that tick, before movement), `startFlight` fires it **only if that pawn is genuinely the ball carrier at that exact moment** — clamping the raw target to `KICK_RANGE` (Euclidean), then `aim.ts`'s `sampleLanding` perturbing it by a skill/distance-scaled spread, same as always. If they're not actually carrying the ball (their plan assumed possession they don't have — e.g. a defender beat them to it earlier in the turn), the kick step silently fizzles: no flight, no event, straight on to whatever step comes next. If `kick.loft` was set, the flight also gets an `apexHeight` (clamped by kick distance, see "Ball height and loft" below); a grounded kick's `apexHeight` is 0. Each tick a flight is active, its height is computed (`heightAlongFlight`, a parabola) and gated against `BALL_REACH_HEIGHT`/`HEADER_REACH_HEIGHT`: at or below the lower threshold `checkCapture` runs, between the two only `checkHeader` runs (see "Heading" above), above both the ball sails over everyone untouched. When `checkCapture` does run, it sweeps the segment the flight covered that tick (not just the endpoint, to avoid tunneling past a defender) against every pawn: a teammate within `CAPTURE_RADIUS` receives it; an opponent gets an `"interception"` contest (or `"gk_claim"` for an Aggressive-stance goalkeeper inside his own box reaching beyond the normal radius — see "Goalkeeper" below) — a decisive win is a clean pick-off (turnover, freezes the turn), a narrow win only knocks the ball loose (a `BallRoll` with friction and a random deflection angle, not a clean takeover). An unopposed flight that reaches its sampled landing point also becomes a loose roll rather than stopping dead. A flight (or the roll it turns into) that exits the pitch without being touched or scored freezes the turn for a dead-ball restart instead — see "Dead-ball restarts and fouls" above.
2. **Movement**: every pawn advances up to `PAWN_SPEED_PER_TICK` (real distance, any direction) toward its CURRENT step's target each tick via `candidateHeadings`, which also tries sidestep angles if the direct line is blocked — a pawn keeps partial progress and can try again next tick rather than being permanently stuck. Reaching a movement step's position (within floating-point tolerance) advances the pawn's step cursor to whatever comes next in its chain; kick steps don't get "arrived at" this way at all (see step 1) — only movement steps consume ticks and distance. Effective per-tick speed is not always the base rate: a `"pressure"`-stance opponent nearby cuts it (`PRESSURE_SLOW_FACTOR`), an active sprint multiplies it up (`SPRINT_SPEED_MULTIPLIER`) — these stack multiplicatively, computed fresh each tick. A `"man_mark"` stance pawn with no explicit plan gets its destination recomputed every tick as a blend toward the marked opponent's live position (`MAN_MARK_PULL_WEIGHT` — mostly pulled toward the target, partly holding ground, not a blind chase); a goalkeeper (any side, any stance including none) with no explicit plan gets its destination recomputed the same way via `gkAutoTarget` (see "Goalkeeper" below). Any explicit `plannedSteps` entry always overrides either. A dribbling carrier who walks the ball out of bounds this tick also freezes the turn for a dead-ball restart, checked right after this step (before the tackle-challenge step below — once it's crossed the line, no tackle can happen after).
3. **Collision**, now pure contest-free geometry (reworked — see "Player-driven tackling and collision rework" below for why): a fixed-point loop each tick runs **Rule 1 (hard block)** — a pawn not vacating its cell this tick can't be entered, no skill check, sidestep angles tried first — followed by an **overlap nudge** pass that pushes any two still-*moving* pawns landing within `PAWN_OVERLAP_RADIUS` of each other's intended position apart along the line between them, just enough to clear it. Neither ever produces an event, a skill check, or any lasting consequence — crossing paths or ending up near another pawn (any side, including teammates) means nothing on its own anymore. **Invariant (relaxed for one case)**: no two pawns may ever be closer than `PAWN_OVERLAP_RADIUS` in any snapshot, *except* a goalkeeper positioned within his own penalty box is exempt from this loop entirely (though he can still legitimately block others by standing still) — modeling a goalmouth scramble rather than two solid bodies that can never overlap. Outside his own box the GK is a normal pawn, fully subject to the general invariant. The invariant has been fuzz-tested (random start/destination pairs, hundreds of trials); preserve it if you touch collision code.
4. **Tackling**, now player-declared rather than automatic — see "Player-driven tackling and collision rework" below for the full mechanic (Clean/Hard, cooldown, the `auto_tackle` stance). A dribbling (non-kicking) carrier can be challenged every tick by the nearest eligible, not-yet-tried opponent within `TACKLE_RADIUS` — a `"tackle"` contest, decisive win = clean turnover (freezes the turn), narrow win = ball knocked loose, a decisive *loss* for the challenger risks a foul (freezes the turn for a free-kick/penalty restart — see "Dead-ball restarts and fouls" above) instead of just doing nothing. A `man_mark` `stanceBonus` (skill+pace-scaled, only against the actual marked opponent) still applies on top of whatever Clean/Hard grants.
5. **Reactions**: any pawn newly within `REACT_RADIUS` of a still-loose ball gets a one-shot `attemptsReaction` roll to abandon its plan and chase it instead (see `reactions.ts`).
6. **Scoring**: if the ball's movement this tick crossed a goal line within the goal-mouth rows (checked at the crossing point, not just the tick's end position, to avoid tunneling — `goalCrossing`, which also returns *where* it crossed), that crossing is **not** an automatic goal — `attemptSave` first checks whether the defending side has a goalkeeper and, if so, runs a `"save"` contest against it (see "Goalkeeper" below). Only if there's no GK, or the GK loses, does `goal` get set and the turn freeze immediately. This check happens at *every* place a goal can be scored — a kicked flight crossing the line, a loose/deflected `BallRoll` crossing it, and a dribbling carrier walking it in (checked once at the very end of the turn, since nothing else watches for that case mid-tick) — not just the obvious kicked-flight path, so a scrappy deflection drifting toward net doesn't get a free pass a deliberate shot wouldn't. On a real goal, `Game.tsx` increments score, resets both sides to kickoff formation, and re-centers the ball.
7. **Per-tick events**: each `ResolveSnapshot` carries the events generated *during that specific tick* (not one flat end-of-turn list) via a running cursor into the shared event log — this is what lets `Game.tsx` reveal the events log in sync with the animation instead of dumping everything after playback finishes. `ResolveSnapshot.ballHeight` rides alongside `ball` for the same reason — the tick-by-tick animation needs a height to lift the sprite by, not just a final resting value.

### Stances and Sprint

Two different categories of per-pawn tactical choice, layered on top of `plannedSteps` rather than replacing it:

- **Stances** (`types.ts`'s `Stance` union) are freely re-selectable every turn, cleared automatically once a turn resolves (`Game.tsx`'s post-turn bookkeeping in `resolveWithPawns`) — **with one deliberate exception**, `auto_tackle`, which persists until the player explicitly changes it (see "Player-driven tackling and collision rework" below). Outfield: `"pressure"` (slows nearby opponents' movement, see step 2 above), `"cover_passing"` (interception-contest bonus), `"man_mark"` (auto-movement blend + contest bonus against one specific opponent, picked via a target-picker click mode in `Game.tsx`), `"expecting_header"` (see "Heading" below — gates header eligibility itself rather than granting a contest bonus), `"auto_tackle"` (hands-off standing order to tackle whenever in range, off cooldown). Goalkeeper: `"gk_on_line"`/`"gk_aggressive"` (see "Goalkeeper" below) — unrelated to tackling, purely GK positioning/claim-eligibility. `Game.tsx`'s `stanceOptionsFor(pawn)` picks which list to offer based on `player.position === "GK"`; there's no type-level enforcement that a `Stance` variant matches the pawn's position (the same pre-existing gap `man_mark` already had) — this is a UI-level guarantee only. Left open to further variants (offensive stances) without needing a redesign.
- **Sprint** is deliberately *not* a stance — it's a cooldown-gated skill (`plannedSprint` + `sprintCooldown` on `Pawn`), since there's no stamina-drain/fatigue resource to draw a numeric cost from; the cooldown lockout is the cost. `sprintCooldown` is the one piece of pawn state that persists and evolves across turn boundaries rather than resetting — `resolve.ts` only reads `plannedSprint` (a pure per-turn function has no notion of "next turn"), while `Game.tsx` sets/decrements `sprintCooldown` in the same post-turn pass that clears stances.
- Both are hidden from the non-controlling side in hotseat the same way `plannedSteps` already is (`MatchScene.ts`'s `updatePawns`); `sprintCooldown` itself stays visible to both sides since it's a public status, not hidden intent.
- Both are now wired into `ai.ts` (see "AI opponent" below) — stances for pressing/marking/covering/expecting a header, sprint for a genuinely long closing/dribbling/recovery leg. The goalkeeper stays the one pawn that never gets a stance from the AI (it always plans an explicit position instead — see "Goalkeeper" below for why that's still correct).

### Ball height and loft

The ball has a live height (meters, same world-unit scale as everything else) during a kicked flight, tracked in `resolve.ts` and animated via `MatchScene`'s `updateBall()`.

- **Choosing loft**: the kick UI (`Game.tsx`'s action panel, shown when `kickMode`) offers a Ground/Loft toggle for shot/pass, stored as `kick.loft` on the `PlannedStep` a kick click appends (see "Multi-step planning and stamina" above). A cross is the one exception to "independent of `kick.kind`": it's unconditionally lofted regardless of the flag, enforced in `resolve.ts`'s `startFlight` itself (`effectiveLoft = kind === "cross" || loft`) rather than trusted from the caller — the UI hides the Ground/Loft row entirely when Cross is selected, and `ai.ts` always sets `loft: true` on the crosses it plans, but the engine doesn't rely on either of those to actually agree. `ai.ts` still only ever plans grounded shots/passes (`loft: false`) — that axis remains a genuine, unexploited tactical choice for the AI to learn later.
- **The arc**: `startFlight` computes an `apexHeight` for the flight (0 for grounded) from `LOFT_APEX_MIN/MAX` clamped against the kick's actual distance — a short loft still clears reach height briefly, a long cross doesn't arc absurdly high. `heightAlongFlight` is a simple parabola over the flight's existing progress fraction (`traveled/totalDist`): 0 at both ends, peak at the midpoint. This is why height needed no new "clock" concept — it rides the same progress value the x/y interpolation already used.
- **`BALL_REACH_HEIGHT`** is the one threshold gating whether *anyone* — teammate or opponent, via `checkCapture` — can touch the ball this tick. Above it, the flight sails on overhead regardless of who's standing underneath. The tick loop gates on `captureGateHeight`, the *higher* of the tick's start/end height (not just the end), because `checkCapture` sweeps the whole segment covered that tick — gating on the endpoint alone would wrongly permit a capture on the exact tick a descending ball crosses back under the threshold, even though it was still out of reach for most of that tick's sweep. This was a real bug caught by the throwaway-script verification pattern before shipping; preserve the start/end-max approach if you touch height gating.
- A grounded kick's height is 0 for every tick by construction (`apexHeight` is 0, so the parabola is 0 everywhere) — there's no separate code path to keep in sync, which is what makes loft additive rather than a rewrite of normal kicks.

### Goalkeeper

Before this, `GK` was a position label with no real mechanics attached — every shot was an unconditional goal the instant it crossed the line, with no save chance whatsoever. This was deliberately built *before* resuming the (paused) header work, since shooting/crossing/heading mechanics on top of an undefended goal was building on sand; an attacking header-on-goal will eventually just be another shot routing through the same save contest built here.

- **Attributes**: three new `PlayerDTO`/`players`-table numbers — `jumping`, `shot_stopping`, `reflexes`. `jumping` is shared conceptually with the (not-yet-built) header work; `shot_stopping`/`reflexes` are GK-specific.
- **Stances**: `"gk_on_line"` (conservative — auto-positioning stays anchored, no proactive claim attempts, reacts only once a shot actually threatens goal) and `"gk_aggressive"` (auto-positioning advances further off the line for a nearby threat, and becomes eligible for the proactive claim below). No stance (`null`) resolves to the same conservative behavior as `gk_on_line` — this is what keeps an AI-controlled or freshly-spawned GK sensible without any `ai.ts` involvement.
- **`gkAutoTarget`** (`resolve.ts`) recomputes a GK's destination every tick it has no explicit plan (`plannedSteps.length === 0`), shadowing the ball's row anchored near goal (depth scales toward `GK_PENALTY_DEPTH` for an Aggressive GK judging a nearby threat) — same `hasExplicitPlan`-gated pattern `man_mark`'s auto-movement already established. An explicit `plannedSteps` entry (manual positioning, e.g. to receive a pass and build out from the back) always overrides this; there's no separate "manual" stance, since this override already exists for every pawn. **This is also why `ai.ts` needed zero changes**: it always sets an explicit plan for its own GK every turn (its pre-existing shadow-the-ball-row rule), so `hasExplicitPlan` is always true for it and `gkAutoTarget` simply never runs for an AI-controlled keeper — the AI's old rule keeps driving it, unmodified, while the save mechanic below still applies to AI matches for free (it doesn't check who's controlling the GK).
- **The save contest** (`contest.ts`'s `"save"` kind, `resolve.ts`'s `attemptSave`): weighted mostly by `shot_stopping` with `reflexes` a smaller factor. `jumping` is deliberately **not** a `WEIGHTS.save` entry — see `reachFactor` in the `contest.ts` bullet above for why an additive term was rejected, and don't reintroduce one. `attemptSave` takes the crossing point and the ball's height, finds the defending side's GK (no GK = automatic goal, same as before this feature existed), and rolls `rollSaveAttempt` against `SAVE_DIFFICULTY_THRESHOLD`; a decisive win catches it cleanly (GK becomes the new carrier), a narrow win parries it into a loose ball near the save point (reusing the same deflection/roll machinery a mishit shot already uses), a loss (or no GK) is a goal.
- **The proactive claim** (`"gk_claim"` contest kind): an Aggressive-stance GK inside his own penalty box is folded into `checkCapture`'s normal candidate list at an expanded `GK_CLAIM_RADIUS` (vs. the generic `CAPTURE_RADIUS` any defender gets) — same downstream handling (decisive win/narrow deflection/loss), just wider eligibility and GK-specific attribute weighting for that one pawn. An On-the-line GK never enters this expanded branch; a normal-radius interception still applies to any GK regardless of stance, same as any other pawn. Losing a claim attempt (or simply committing to one) leaves the GK genuinely out of position for whatever happens next — no separate "recovery" state needed, since his position is just wherever the attempt left him, and movement for the tick already resolved before `checkCapture` runs.
- **The GK's own box** (`GK_SIX_YARD_DEPTH`/`GK_PENALTY_DEPTH`/`GK_PENALTY_PAD` in `constants.ts`) is shared between rendering (`MatchScene.ts`'s `redrawField` box outlines) and gameplay (`resolve.ts`'s `withinPenaltyBox`, used by the claim eligibility check and the collision relief in step 3 above) — one source of truth, so "inside the drawn box" and "inside the gameplay box" can't drift apart.
- **Deferred, not forgotten**: a goalkeeper-specific event/UI polish pass.

### Heading

Built directly on top of the goalkeeper/save work — an attacking header-on-goal is just another shot routing through the same `attemptSave` contest, so it needed the goalkeeper to exist first.

- **`HEADER_REACH_HEIGHT`** (3.2m, above `BALL_REACH_HEIGHT`'s 2.2m) is a second height band in the tick loop's `captureGateHeight` check: at or below `BALL_REACH_HEIGHT` a ball is normal-capturable, between that and `HEADER_REACH_HEIGHT` it's headable only (`checkHeader` instead of `checkCapture`), above both it's fully untouchable. Grounded/low balls never reach headable height at all — heading only ever triggers off a loft.
- **`checkHeader`** (resolve.ts) sweeps the tick's segment for any pawn (either side) within `HEADER_RADIUS`, excluding the flight's own kicker (can't head your own pass), anyone already in `flight.contested`, **and anyone whose stance isn't `"expecting_header"`** this turn — added after an early version let *anyone* merely standing near a flight's path auto-contest it, which made an ordinary lofted pass between two teammates involuntarily turn into a header duel the instant it crossed headable height. A pawn who never expected the ball to arrive that way just lets it sail past untouched until it descends low enough for a normal capture; only a pawn who deliberately anticipated the cross (attacker or defender — the stance is symmetric, in `OUTFIELD_STANCE_OPTIONS`) is even eligible. Three cases from there: 0 eligible pawns, nothing happens, flight continues untouched. 2+ eligible pawns is a genuine `resolveContestDetailed(..., "header")` contest — always produces a clean winner, no separate fail chance (unlike tackle/interception there's no `DECISIVE_CONTEST_MARGIN` split here yet). Exactly 1 eligible pawn is the interesting case: rather than an automatic win, it still rolls via `rollHeaderAttempt` against `HEADER_DIFFICULTY_THRESHOLD` — clearing it is a clean header, failing it is a fluff (ball squirts loose, same deflection shape `checkCapture`'s narrow-win case already uses, tracked via `HeaderOutcome.fluffedBySide`). **This "always roll, even uncontested" behavior was a deliberate, explicit user override** of the more conventional "auto-win when uncontested" design — the reasoning: a player should still occasionally fluff an unmarked header (poor skill, or a future situational modifier like coming off a defender's pressure/imbalance), so the roll needs to exist now even before those modifiers do, rather than being retrofitted later.
- **Fully automatic target selection**: a won header has no planning UI at all — `pickHeaderTarget` runs mid-resolution regardless of who's "controlling" the winning pawn that turn, mirroring `ai.ts`'s shoot/pass/dribble shape (shoot on goal if within `KICK_RANGE` with a clear lane via `hasHeaderLane`; else pass to the most advanced open teammate; else clear the ball upfield by `HEADER_CLEARANCE_DISTANCE` along the winner's own attacking direction) but implemented fresh here since it must work for *either* side in the same turn, unlike `ai.ts` which only ever plans one side. A clean header becomes a genuine new `BallFlight` (via `startHeaderFlight`), not a carrier handoff — the ball stays airborne and whatever eventually receives/intercepts/saves it gets its own existing freeze semantics, unchanged.
- **Attribute split**: `jumping` is the dominant `WEIGHTS.header` factor (winning the contest — a *different* role than its gating function in the GK save formula, see the `contest.ts` bullet above), `heading` governs `aim.ts`'s landing spread for the redirect once a header is won (a high-heading pawn redirects more precisely; it has no bearing on whether the header is won at all).

### Dead-ball restarts and fouls

When the ball leaves the pitch or a tackle goes badly wrong, play stops for a restart rather than the ball just drifting to a dead stop at the boundary (the old, restart-unaware behavior).

- **`boundaryCrossing(from, to)`** (resolve.ts) mirrors `goalCrossing`'s segment-interpolation shape (a fast roll/deflection can jump clean past a boundary within one tick, so the endpoint alone isn't enough) — covers the touchline and the goal line **outside** the goal mouth (`!isInGoalRows`, the goal-mouth case stays fully owned by `goalCrossing`/scoring, untouched). When a tick's segment could cross both within one tick (a diagonal exit near a corner flag), the crossing with the smaller interpolation `t` wins — physically "whichever happened first," not a fixed check-order.
- **`DeadBallResult`** (`{ type, side, spot }`, on `ResolveResult.deadBall`) is `null` on every ordinary in-play turn. `type` is `"throw_in" | "corner" | "goal_kick" | "free_kick" | "penalty"`; `side` is who's **awarded** the restart; `spot` is where the ball is placed **and** where `Game.tsx` snaps the single nearest eligible pawn of `side` to take it — no full formation reset, everyone else stays exactly where the run of play left them. `classifyDeadBall` handles the boundary-crossing three (a defender's own touch sending it behind their line is a corner; an unopposed shot going wide is a goal kick; a touchline exit is always a throw-in to whoever didn't touch it last) using new `touchedBySide`/`deflectedBySide`/`fluffedBySide` tracking on `BallRoll`/`CaptureOutcome`/`HeaderOutcome` — distinct from the pre-existing `lastControllingSide`, which only tracks genuine possession changes, not mere deflections/parries/half-tackles/fluffs.
- **Quick vs. extended setup**: every restart type freezes the turn and immediately places the ball (Increment A's behavior = "quick restart"). On top of that, the awarded side (and only that side — no second decision point for the opponent, matching how a real quick free kick/throw works) gets a one-time full-screen choice (`Game.tsx`'s `pendingRestart` state, reusing the same full-screen early-return pattern as the hotseat handoff prompt) between taking it immediately or calling for **extended setup**: a fixed number of extra turns (`restartSetup.ts`'s `SETUP_TURNS_BY_TYPE` — throw-in 1, corner 2, goal kick 1, free kick 3) resolved via `resolveSetupTurn` instead of the live `resolveTurn`, where both sides can reposition and change stances (including man-marking) with the ball dead at a fixed spot the whole time. There's no bailing out once "extended" is chosen — all bonus turns play out before the restart can actually be taken; the strategic tension is meant to live entirely in the upfront choice. A restart falling to a side with no human decision-maker (an AI's own restart, or solo mode's passive away side) always takes it quickly — `ai.ts` needed zero changes for this, since `resolveSetupTurn` simply never gets invoked for those restarts.
- **Saved corner-kick presets**: during a corner's extended setup, if it's `home`'s own corner (never a defensive setup — see below for why), the HUD banner grows two buttons: "Save as my preset" captures every home pawn's *current* position as an offset from the dead-ball spot in an attack/touchline-relative frame (`Game.tsx`'s `cornerPresetOffset`/`applyCornerOffset`) — `alongAttack` = distance out from the goal line, `alongTouch` = distance toward the pitch's center from the corner's own near touchline, both derived from `deadBall.side` and which of the two same-end corners `spot` is at. That frame (not raw world x/y) is what lets one saved preset correctly re-apply at *either* of a team's two attacking corners, and in either home/away orientation, without needing separate presets per corner or per match — verified both with a pure geometry script (round-trips exactly at the same corner; mirrors correctly to the opposite corner of the same end; mirrors correctly for the away attacking direction) and live end-to-end (saved real pawn positions, applied them back, got the exact originals). "Apply my preset" does the inverse: `fetchCornerPreset` then sets each home pawn's `plannedSteps` to a single computed waypoint, same as a normal manual click would — the player still has to click Continue/Ready to actually walk there over the remaining setup turns; nothing here bypasses `resolveSetupTurn`. Persisted per-team in the backend's `team_corner_presets` (opaque JSON blob — the frontend is the only thing that ever interprets it). **Deliberately corner-only, not free-kicks**: a foul's location varies continuously across the whole pitch, so a single flat preset wouldn't generalize the way it does for a corner's fixed, small set of spots. **Deliberately attacking-only, not defensive setups**: a defensive shape depends on the opponent's own formation, which isn't something a flat preset can usefully capture — gated on `deadBall.side === "home"`.
- **Fouls**: a tackle challenge the challenger *decisively loses* (margin past `DECISIVE_CONTEST_MARGIN`, i.e. a genuinely bad, mistimed lunge — a narrow loss never risks this) has a chance of being ruled a foul instead of just failing silently, scaling up the worse the loss (`FOUL_CHANCE_AT_THRESHOLD` → `FOUL_CHANCE_MAX` over `FOUL_CHANCE_MARGIN_RANGE`). A Hard tackle gets a flat `HARD_TACKLE_FOUL_BONUS` added on top of that (was `"aggressive"`-stance-driven, now an explicit Clean/Hard choice — see "Player-driven tackling and collision rework" below) — a real risk/reward trade-off against Hard's existing tackle-contest bonus, not a pure upside. `classifyFoul` checks `withinPenaltyBox(holder.pos, challenger.side)` (the *fouling* side's own box) to decide **penalty** (fixed spot at `PENALTY_SPOT_DEPTH`, kicker vs. keeper, reusing the save contest completely unchanged) vs. **free kick** (spot = exact foul location, goes through the same quick-vs-extended pipeline as any other restart). A penalty deliberately **never** gets the quick-vs-extended prompt at all — a 1-on-1 penalty has no "organize a wall" concept to opt into.
- **No card/suspension system yet** — deliberately deferred, not blocked: the foul is detected at one clear point in `resolve.ts` with both the fouler and the fouled player already identified, which a future discipline system can hook into without any rework here.
- **Explicitly out of scope for now**: offsides (planned for the future 11v11 phase) and free-kick presets (see the corner-preset bullet above for why a flat preset doesn't generalize the same way to a foul's continuously-varying location). Substitutions now exist, but only within Career mode — see "Career mode" below; there's still no bench/reserve-roster concept for hotseat/solo modes.

### Player-driven tackling and collision rework

Tackling used to be fully automatic (any nearby opponent challenged the carrier, every tick, no player choice at all), and ordinary movement collision used to run a `"loose_ball"` skill contest between ANY two pawns — including teammates — that merely crossed paths or ended up near each other, freezing the loser for the rest of the turn. Both were rebuilt together, directly off two user complaints after playtesting: tackling wasn't legible or controllable, and the collision freeze was a leftover from the game's old grid-based movement model (losing "the turn" meant losing one small discrete step back then; now a turn can be many ticks of continuous, multi-leg movement, so an incidental near-miss could silently waste an entire plan).

- **Tackling is now a player-declared skill** (`Pawn.plannedTackle: { kind: "clean" | "hard" } | null`, turn-scoped like `plannedSprint`) rather than automatic. The tackle-challenge check (see "How a turn resolves" above) now only considers opponents who are off cooldown (`tackleCooldown === 0`) AND have either declared `plannedTackle` this turn or have the standing `"auto_tackle"` stance active — everyone else is simply not eligible, regardless of proximity. `Game.tsx`'s action panel gets a `Tackle` button (mirrors `Sprint`'s disabled/cooldown-label shape) that reveals a Clean/Hard sub-row when opened (mirrors Kick's Shot/Pass/Cross row) — picking a kind sets `plannedTackle` directly (no field click, unlike a kick) and closes the sub-row; picking the same kind again clears it.
- **Clean vs. Hard** is a direct, faithful split of what the old always-on system already did: Clean is the baseline roll (no bonus, no extra foul risk) — what every tackle effectively was before this stance existed at all; Hard is the old `"aggressive"`-stance behavior made explicit (`HARD_TACKLE_PACE_FACTOR` contest bonus + `HARD_TACKLE_FOUL_BONUS` on a bad miss, both in `constants.ts`, both the same numeric values the retired stance used). `contest.ts`'s `tackleTypeBonus` applies this — deliberately a **separate** function from `stanceBonus`, not folded into it, since `plannedTackle` and `stance` are independent fields now (a pawn can be `man_mark`-ing a specific opponent AND declaring a Hard tackle on them in the same turn; folding Hard's bonus into `stanceBonus`'s early-return chain would silently drop one bonus or the other). `auto_tackle` firing with no explicit `plannedTackle` set always defaults to Clean — the safe, hands-off choice; a player who wants Hard's risk/reward has to declare it explicitly.
- **The outfield `"aggressive"` stance is retired outright** — its only effect was the tackle bonus/foul-risk bump above, fully superseded by the explicit Clean/Hard choice. (GK's separate `"gk_aggressive"` stance is unrelated and untouched.)
- **`auto_tackle`** is the one stance that does **not** reset to "None" every turn the way every other stance does — it persists until the player explicitly changes it (`Game.tsx`'s post-turn bookkeeping special-cases it: `stance: p.stance?.kind === "auto_tackle" ? p.stance : ...`). A deliberate, one-off exception, chosen specifically so "set a defender to auto-tackle" reads as a lasting assignment rather than something to re-click every turn.
- **Cooldown + speed penalty**: any tackle attempt — clean win, scrappy loose-ball knock-loose, miss, or foul, any outcome — costs the challenger `TACKLE_COOLDOWN_TURNS` (1) of `Pawn.tackleCooldown`, during which their effective per-tick speed is halved (`TACKLE_COOLDOWN_SPEED_FACTOR`, stacks multiplicatively with pressure/sprint the same way those already do) and they can't enter another challenge. Whether an attempt *actually happened* (not just whether one was *declared*) can only be known after resolution — a declared/auto tackle that never got within `TACKLE_RADIUS` of the carrier shouldn't cost anything — so `resolveTurn` now returns `tacklesAttempted: string[]` on `ResolveResult` (pawn ids that entered at least one challenge that turn, tracked separately from the pre-existing `tackleAttempted` Set, which resets whenever the carrier changes and exists for a different purpose — stopping the same defender getting a free re-roll against a *new* carrier). `Game.tsx` reads this the same post-turn pass it already uses for `sprintCooldown`.
- **Collision is now pure, contest-free geometry** (see "How a turn resolves" step 3 above for the mechanism) — the old Rules 2/3 (`"loose_ball"` swap/group contests, whole-turn freeze) are deleted entirely, not tuned. `PAWN_COLLISION_RADIUS` (1.4, a "personal space" bubble) is replaced by `PAWN_OVERLAP_RADIUS` (0.3, "just don't literally overlap") everywhere it was used: Rule 1's hard-block radius, `restartSetup.ts`'s own simplified "find a clear spot" pass, and (removed rather than shrunk, since a 0.3-unit ring isn't a meaningful tuning aid) `MatchScene.ts`'s debug influence overlay. Per an explicit user principle: pawns (any side, including teammates) are free to cross paths and brush past each other; the only thing that still matters is not ending up at the exact same point. `TACKLE_RADIUS` (1.7) comfortably exceeds `PAWN_OVERLAP_RADIUS`, which is what guarantees a tackle-eligible defender's approach always trips the real tackle-challenge check first — there's no second, duplicate "steal the ball via contact" path hiding in the collision code.
- **`ai.ts` needed an explicit update** or its defenders would have simply stopped tackling once the always-on system was removed: the `"press"` intent's `aggressive: boolean` field is renamed `willTackle` (same computation — within `TACKLE_PROXIMITY_AGGRESSIVE_FRACTION * TACKLE_RADIUS` of the carrier) and `realizePawnIntent` now sets `plannedTackle: { kind: "hard" }` when `willTackle` is true and the pawn is off cooldown, gated the same way `maybeSprint` gates sprint. Pressing (the `"pressure"` stance, slows the carrier) and tackling are independent now rather than a forced either/or — a presser gets both effects at once when close enough, which is a strict improvement, not just a mechanical necessity. The AI always declares Hard, never Clean — it has no risk-aversion model to pick Clean with today; a natural future `TacticalProfile` hook, not built.
- **Verified via the throwaway-tsx-script pattern** (see "Commands" above) before this was considered done: teammates crossing paths at a range that used to trigger a freeze now both complete their full plan with zero events; Clean vs. Hard produce measurably different win/foul rates in repeated trials against identical opponents; a pawn on cooldown can't enter a new challenge and moves at exactly half the per-tick speed of an otherwise-identical off-cooldown pawn; and a 300-trial fuzz test (12 pawns, random start/destination pairs) never once observed two pawns closer than `PAWN_OVERLAP_RADIUS`.

### Multi-step planning and stamina

The last major "one destination or one kick per turn" limitation — a pawn now plans a whole **chain** of waypoints and/or kicks for the turn, built by clicking repeatedly (DOS2-style) rather than click-and-replace. This was the biggest structural rework of the session: `resolveTurn`'s tick loop went from a fixed `MOVE_RANGE`-tick loop with one precomputed destination per pawn to a variable-length, per-pawn step-cursor model (see "How a turn resolves" above).

- **`PlannedStep`** (`types.ts`) is `{ pos: Vec2; kick?: { loft: boolean; kind } }` on `Pawn.plannedSteps: PlannedStep[]` (`kind` — "shot"/"pass"/"cross" — added later, see "Shooting, Passing, and Crossing" below). For an ordinary step, `pos` is a destination to walk to. For a kick step, `pos` is the kick's **aim target**, not a place to walk — the kick fires from wherever the chain has already left the pawn (the previous step, or its real position if the kick is first), consuming zero movement distance. A kick can appear **anywhere** in the sequence, not just at the end — "move, kick, then keep moving (now ball-less)" is a fully valid plan, per an explicit user call: multi-step planning should support arbitrary interleaving, not just an optional trailing kick.
- **Charges, not extra range**: `chargesFor(player)` (resolve.ts) = `STAMINA_CHARGES_BASE + floor(stamina / STAMINA_PER_BONUS_CHARGE)` — this governs how many separate **actions** (a movement leg costs 1, a kick step costs `KICK_CHARGE_COST`) a turn's plan can have, **not** how far a pawn can travel in total. `PAWN_MOVE_BUDGET` (the pre-existing single-turn distance cap) stays exactly what it always was regardless of charge count — a first pass let charges multiply total range (more charges = a bigger total budget), which very visibly broke the game feel (pawns moving 3-4x further per turn than before) and was deliberately corrected: `STAMINA_CHARGES_BASE = 1` guarantees every pawn can always at least plan one ordinary destination exactly as before this system existed; bonus charges only buy the ability to **subdivide** that same fixed budget into more/shorter legs (or spend some of the budget on a kick action instead). `clampStepsToBudget` (resolve.ts) is the defensive backstop — mirroring `startFlight`'s `KICK_RANGE` clamp — stopping at the first step that would exceed either the charge count or the cumulative movement distance, in case the UI's own gating (`Game.tsx`'s `chargesRemaining`/`distanceRemaining`) is ever bypassed.
- **`Game.tsx`**'s click handling: Move mode appends a waypoint extending from `chainEndPosition(pawn.pos, plannedSteps)` (the last MOVEMENT step's destination, or the pawn's real position if the chain has none yet or only kicks so far — a kick step never moves this); clicking back near that point undoes the last step (whatever kind it was). A move click beyond what's actually reachable doesn't get silently ignored — it clamps to the edge of the reachable distance in the direction clicked, so a slightly-overshot click still plans a waypoint instead of doing nothing. Kick mode is available whenever a charge remains — **not** gated on already holding the ball, since a chain might walk to it first; the engine's own fizzle behavior (see below) is what makes an overly-optimistic queued kick harmless rather than a crash. **At most one kick step is ever kept in a pawn's plan**: placing a kick click filters out any kick step already queued (anywhere in the chain) before appending the new one — a pawn genuinely can't fire two kicks in one turn (no ball left after the first), so a second kick click means the player is reconsidering type/direction, not adding a second action, and the plan enforces that rather than just hoping the UI flow prevents it. A kick click flips back to Move mode afterward, but stays **selected** either way, so the same pawn keeps taking clicks until the player selects someone/something else. Right-click undoes the last step when there is one, or deselects the pawn entirely once the plan is empty (`handleViewportContextMenu`) — also suppresses the browser's native context menu, which nothing else in this game needs. (See "Camera, input, and HUD polish" below for the two other, later-added ways to deselect — Escape, and a field click once the move budget's spent.) **`handlePawnClick` redirects to the field-click handler whenever `kickMode` is active and a pawn is already selected** — aiming a kick *at* a pawn (a cross to a teammate's head, a shot past a keeper) is common and legitimate, but Phaser's default `topOnly` input means a click landing on a pawn's own hit area never reaches the field zone underneath it; without this redirect it silently reselected/deselected the clicked pawn instead of placing the kick.
- **Fizzling**: a kick step only actually fires if the pawn is `currentCarrierId` at the exact tick its cursor reaches that step. If a tackle, interception, or reaction changed possession earlier in the turn and the plan's bet didn't pay off, the step is silently skipped (no event, no crash) and the pawn just proceeds to whatever step comes after it, if any.
- **`MatchScene.ts`**'s planned-move overlay draws the whole chain as one connected sequence: movement legs as a yellow polyline (small circle at an intermediate stop, the full destination ellipse at a stopping point — the last step overall, or right before a queued kick), kick steps with the same aim-preview styling (color by loft, aim-spread ring, risk-label readout) a single kick has always had — critically, a kick step does **not** advance the polyline's cursor, since it doesn't move the pawn. The reach-circle origin (`updateReachHighlight`) follows the same `chainEndPosition` logic in both Move and Kick mode.
- **Untouched by this increment**: `resolveSetupTurn` (dead-ball extended-setup turns) deliberately stays single-waypoint only — it reads just `plannedSteps[0]?.pos`, ignoring any `kick` field or further steps entirely, since a stoppage is background positioning, not the core gameplay loop. `ai.ts` now genuinely uses multi-leg chains too (see "AI opponent" below) — a carrier with a spare charge can dribble a leg and then re-evaluate a shot/pass from the projected position, chaining both into one plan via the same `buildChain` self-clamping constructor every other AI branch funnels through.
- **`Game.tsx`'s state** was later consolidated into one `MatchState` object (`pawns`, `ball`, `ballHeight`, `turn`, scores, `controllingSide`, `readySides`, `pendingRestart`, `restartSetup`, `events`, `resolving`, `scorers`) bundled into a single `useState`, matching this section's final `plannedSteps` shape — genuinely per-viewer UI/input state (camera, which kick-mode toggle is open, `selectedId`, `benchedPlayers`/`subReplacement`, `aiTacticalProfile`) deliberately stayed as separate hooks, since that's not shared match truth. Fullscreen (`isFullscreen`/`onToggleFullscreen`) is a required prop pair now, not local state — see the Camera/HUD polish section's fullscreen bullet below. Career mode's own props (`homeTeamId?`/`awayTeamId?`/`humanSide?`/`humanStartingPlayerIds?`/`onCareerMatchEnd?`, all optional and only ever set together) are covered in "Career mode" above/below — see also "The human genuinely plays home or away" below for `humanSide`.

### Shooting, Passing, and Crossing

Every kick used to resolve through the exact same accuracy formula no matter what it was for — an earlier `kickIntent.ts` module *guessed* shot/pass/clear from a kick's target geometry, but that guess was purely cosmetic (an aim-ring label), never fed back into the engine. Prompted directly by the `expecting_header` fix above: a routine short pass and a deliberate cross into the box were mechanically identical, which made both feel wrong in one direction or the other. A later balance pass made all three kinds genuinely distinct (see below), driven directly by a user call: "crossing essentially means passing through the air," and shooting needed to stay the single most reliable way to score even though a well-placed pass or cross can still find the net.

- **The player declares it, the engine doesn't guess**: `PlannedStep.kick.kind: "shot" | "pass" | "cross"` is set explicitly in `Game.tsx`'s Kick-mode action panel (a Shot/Pass/Cross row). `kickIntent.ts` (`classifyKickTarget`/`KickIntent`/`intentLabel`) is deleted entirely — nothing infers intent from geometry anymore. `ai.ts` now declares all three (see "AI opponent" below), not just shot/pass.
- **All three kinds now resolve differently.** `aim.ts`'s `landingSpread(distance, skill, kind, onTarget?)`:
  - **`"cross"`** swaps in a steeper `CROSS_DISTANCE_SPREAD_FACTOR` (roughly double the normal `DISTANCE_SPREAD_FACTOR`) — `BASE_SPREAD`/`SKILL_SPREAD_FACTOR` stay shared, which is what makes a *short* cross land almost like a lobbed pass (both formulas converge as `distance → 0`) while a *long* one scatters much more. It's also **unconditionally lofted** regardless of the Ground/Loft toggle (a real football cross is an aerial ball, not a ground pass — see "Ball height and loft" above for how `resolve.ts` enforces this itself rather than trusting the caller), and the Ground/Loft row is hidden in the UI when Cross is selected since it no longer applies.
  - **`"pass"`** keeps the same (tighter) spread shot/cross used to share, but is capped at `PASS_RANGE` (`KICK_RANGE / 2`) instead of the full range — a pass trades reach for nothing, since it already had good accuracy; this is what stops a pass from just being a safer cross at the same distance.
  - **`"shot"`** keeps the full `KICK_RANGE` and the shared spread, but tightens further (`SHOT_ON_TARGET_SPREAD_FACTOR`, ~45% tighter) when `resolve.ts`'s exported `isShotOnTarget(carrierPos, aim, side)` returns true — a ray-based check (does the straight line from carrier through the aim point cross the goal mouth's y-range at the goal line, not just "is the clicked point inside the goal mouth," so it still counts even when `KICK_RANGE` left the aim point short of the line). This is what keeps shooting the most reliable route to goal despite `PASS_RANGE`/`CROSS_DISTANCE_SPREAD_FACTOR` leaving the door open for a pass or cross to score too.
- **The live "mortar aim" preview, built**: `MatchScene.ts`'s overlay tracks the cursor continuously in kick mode (a `pointermove` listener on the field zone, not just reflecting the plan once a step is committed) and, for a cross specifically, draws a real parabola between the pawn and the (range-clamped) cursor — sized from the *actual* `LOFT_APEX_MIN/MAX/HEIGHT_RATIO` formula `resolve.ts` flies with (`apexHeightPx` in `MatchScene.ts`, converted through the same `BALL_HEIGHT_PX_PER_UNIT` scale `updateBall()` uses), not an arbitrary decorative bulge — so the arc you see while aiming genuinely resembles the path the ball will take. The committed-plan overlay (after a kick step is placed) draws the same real arc for *any* lofted kick, not just cross. The accuracy ring's radius is recomputed on every `pointermove` too, so it visibly grows/shrinks as the cursor moves before you commit, using the same `landingSpread` formula the engine actually samples from.
- **The blanket orange reach-circle tint only shows for shot/pass now, not cross** (`MatchScene.ts`'s `updateReachHighlight`, gated on `kickKind !== "cross"`). It was removed entirely at first, on the reasoning that the live accuracy ring already shows real risk at the cursor — but that reasoning only holds for cross, which is the only kind with a live per-cursor preview; shot/pass have no such preview and still need the blanket tint to show how far they can actually reach. The goal-mouth tint and the green teammate pass-halo stay unconditional either way, since those mark specific, useful sub-regions rather than "everywhere you could possibly click."
- **`expecting_header` gets its promised payoff here**: `contest.ts`'s `stanceBonus` gains a `stance.kind === "expecting_header" && kind === "header"` branch, scaled by `jumping` (`STANCE_EXPECTING_HEADER_JUMPING_FACTOR`, constants.ts) — same shape as every other stance bonus, applying to **whoever** has the stance regardless of side. Explicitly **not** a ball-accuracy effect (a defender's anticipation was deliberately kept from degrading the incoming cross — "there are more defenders than attackers usually," making a per-defender accuracy penalty stack unfairly); it only makes an already-eligible header attempt (contested or the single-pawn `rollHeaderAttempt` roll) more likely to succeed. Worth being honest about: since `checkHeader`'s eligibility *already* requires this exact stance, this bonus doesn't create new separation between "anticipated" and "didn't" — the eligibility gate already does that. What it adds is a real, measurable edge for anyone who correctly gets into the duel at all, on both sides.
- **`resolve.ts`**: `startFlight(carrier, rawTarget, loft, kind)` picks the range (`PASS_RANGE` vs `KICK_RANGE`) and computes `onTarget`/`effectiveLoft` from `kind`, then threads the result to `sampleLanding`; the event log differentiates the verb ("shoots" / "plays a pass" / "sends in a cross"). `startHeaderFlight` (an automatic header redirect, not a player-declared kick) is untouched — it has no `kind` to classify, and defaults to `"pass"`'s plain formula.

### Kickoff coin toss

`Game.tsx`'s initial team-load effect randomizes who actually starts with the ball at the match's TRUE opening kickoff — investigated directly off a user report that "only one team ever starts with the ball," which turned out to trace back to a since-fixed `formation.ts` bug (see above): with that bug, every surplus roster player piled up exactly on the ball's kickoff position, and since `resolve.ts`'s carrier check (`current.find(p => distance(p.pos, ball.pos) <= CAPTURE_RADIUS)`) takes the *first* pawn in array order and home's pawns are always listed first, home deterministically "won" every kickoff. With `formation.ts` fixed, both sides' formation forwards actually sit well outside `CAPTURE_RADIUS` of a centered ball (~7-8 units away, `CAPTURE_RADIUS` is 1.2) — so without this feature, a kickoff would just be a neutral, unclaimed scramble every turn, no bug but no real "kickoff" either. `Math.random() < 0.5` picks a side; that side's central forward (the formation's last slot — `FWD` in `FORMATION_6V6_DEFAULT`) is teleported exactly onto `BALL_START`, guaranteeing they carry it, matching how a real kickoff always starts in someone's possession. Deliberately scoped to this one initial load only — post-goal `kickoffFormation` resets are untouched and stay a neutral scramble; a coin toss is a pre-match ritual, not a per-goal one. Verified live across several fresh matches (both home and away won the toss across trials, confirmed via direct match-state inspection).

### Hotseat multiplayer and hidden information

`Game.tsx` holds `controllingSide`, `readySides`, and `handoff`. Each side plans only its own pawns (`handlePawnClick` gates by `controllingSide`), then clicks "Ready" (`handleReady`). If the other side isn't ready yet, a full-screen handoff prompt ("Pass the computer") hides the board until the next player clicks through; when both sides are ready, `resolveTurn` runs automatically. `MatchScene.ts`'s `updatePawns` strips `plannedSteps`/`stance`/`plannedSprint` from the non-controlling side's pawns before rendering, so a player can't see the opponent's queued intent. There is no server-side authority or actual separation between the two "players" — this is local/same-screen only, by design. (A separate in-game test-environment mode, rather than relying on hotseat for testing, has been discussed but not built — "Solo mode" below is the current stand-in.)

### AI opponent (`game/ai.ts` + `game/tacticalProfile.ts`)

Overhauled from an early rule-based stub (single destination-or-kick per pawn, no stances/sprint, predating headers/dead-ball-restarts/multi-step planning entirely) into a substantially more complete rule-based opponent — still no search/minimax/ML, just a much fuller set of rules that now actually uses every system above. `planAiTurn(pawns, ball, aiSide, profile = DEFAULT_TACTICAL_PROFILE)` returns a full `Pawn[]`, `aiSide`'s pawns replaced with real plans, everyone else untouched — same external contract as before, called the same way from `Game.tsx`.

- **Three phases**, mirroring the shape of a real plan-then-execute AI without being architecturally heavier: `assessSituation(pawns, ball, aiSide)` builds a read-only `TeamContext` (teammates/opponents/own GK/carrier/goal geometry, all derived from `constants.ts`, never a hardcoded pitch dimension); `decideTeamIntents(context, profile)` does a **strict three-way dispatch** on ball state — loose ball / opponent has it / we have it, each producing one `PawnIntent` per pawn (a local discriminated union: `carrier_shoot`/`carrier_cross`/`carrier_pass`/`carrier_dribble`, `press`/`man_mark`/`cover_passing`/`expect_cross_defensively`/`hold_shape`, `support_attack`/`support_hold`, `chase_loose_ball`/`cover_loose_ball`, `gk`) — no overlapping cases, so exactly one branch ever decides a given pawn's role that turn; `realizePawnIntent` turns each intent into `{ plannedSteps, stance, plannedSprint, plannedTackle }` — see "Player-driven tackling and collision rework" below for how `press` populates that last field.
- **Carrier detection was fixed along the way**: the original AI checked exact float-position equality against the ball, which stopped matching once positions went continuous (same class of bug `hasClearLane` was already built to avoid). `findCarrier` now uses the identical `CAPTURE_RADIUS` check `resolveTurn` itself starts a turn with, checked over *all* pawns — so the AI correctly reads when the opponent has the ball too, not just itself.
- **The carrier's decision tree** (shoot → cross → pass → dribble-then-kick) funnels every candidate through one `evaluateKick` using the real `aim.ts`/`resolve.ts` formulas (`landingSpread`, `isShotOnTarget`) rather than a separate guess, so the AI's risk tolerance is anchored to the actual accuracy model. A carrier with a spare stamina charge (`chargesFor(player) > 1`) projects a dribble leg forward and re-evaluates shoot/pass **from that projected position**, chaining both into one multi-step plan via `buildChain` (the AI's own shared, self-clamping plan constructor — every branch funnels through it so no AI-produced plan ever needs `resolve.ts`'s defensive `clampStepsToBudget` to save it from an over-budget input).
- **Off-ball shape is now real**, not "one chaser, everyone else drifts": defensively, a presser engages only once the threat is within a distance of the AI's own goal (scaled by the profile — a low-press team simply never engages that far up the pitch), man-marking targets the most advanced unengaged opponents at a count that's a **fraction of the actual opponent roster size** (never a fixed number, so it survives a future squad-size change automatically), one spare covers the passing lane, and — the headline fix — the defense reads the **opponent's own already-queued plan** for a `kick.kind === "cross"` (the human has finished planning by the time `planAiTurn` runs, so this is reading input data, not telepathy) and assigns one defender `expecting_header`. Attacking, off-ball teammates rank by advancement and a profile-scaled fraction gets sent forward as support runs; whichever pawn the carrier designated as its cross receiver always gets `expecting_header` too, **and specifically runs to the cross's own aim point** (not a generic advance-toward-goal spot) so it's actually there when the ball arrives — an early version used the generic run target for this pawn too, which let it drift away before the flight landed and meant headers could never actually fire despite being "planned."
- **`"man_mark"` realizes with an intentionally empty `plannedSteps`** — `resolve.ts`'s own auto-follow (`MAN_MARK_PULL_WEIGHT`, live every tick) only activates when a pawn has *no* explicit plan at all; giving a marker even one explicit step would permanently defeat that engine behavior in favor of one stale snapshot destination.
- **Sprint** (`maybeSprint`) triggers on a carrier's dribble, a presser's/chaser's closing leg, or a defensive-shape recovery leg once the *raw, uncapped* distance clears a profile-scaled threshold and the pawn's cooldown is clear. A real bug caught during verification: several branches used to compute a distance-capped destination *before* deciding whether to sprint, so the sprint speed multiplier had nothing left to actually extend — fixed by always deciding sprint off the true distance to the real target and letting `buildChain` (sprint-aware) do the actual clamping.
- **The goalkeeper is deliberately untouched**: always an explicit shadow-the-ball-row plan (`gkTarget`, now sourced from `GK_ANCHOR_DEPTH` instead of a bare literal), same as before — which is *why* `resolve.ts`'s `gkAutoTarget` still never runs for an AI keeper (see "Goalkeeper" above). Switching the AI's GK to stance-driven (`gk_on_line`/`gk_aggressive` + empty plan) would activate that strictly-more-capable auto-positioning, but it's a real behavior change with no requirement driving it yet — flagged as the natural home for a future `TacticalProfile.gkAggression` field, not built.
- **`tacticalProfile.ts`**'s `TacticalProfile` (9 fields: defensive line depth, pressing trigger distance, marking coverage, attacking commitment, supporting-run depth, shooting range, pass/cross risk tolerance, cross bias, sprint aggressiveness) is threaded through every `decide*`/`realize*` helper as an **explicit parameter**, never a module-level implicit default, so a caller substituting a different profile requires zero changes to `ai.ts`'s control flow. Every field is either a fraction of the actual roster/pitch passed in at runtime, or a multiplier on an existing `constants.ts`/`aim.ts` value — never a bare absolute number — so a future balancing pass (different pitch size, different `PAWN_MOVE_BUDGET`, different player counts) only means retuning what these multiply against, not restructuring the decision logic. `ai.ts` itself carries a matching set of module-level "balance-robust" constants (e.g. `PRESS_ENGAGE_BASE_FRACTION`, `CROSS_TARGET_DEPTH_FRACTION`) that every profile shares as its baseline — these live in `ai.ts`, not `constants.ts`, since they're AI heuristics rather than engine mechanics. **This seam is now actually used, not just built**: Career mode's `team_tactics` table (see "Career mode" below) persists a real per-team `TacticalProfile`, owned by that team's manager (see "Manager system" below) and reachable read-only via the `Managers.tsx` screen rather than a player-facing editor, and `Game.tsx` fetches the AI-controlled side's own saved profile (falling back to `DEFAULT_TACTICAL_PROFILE` if it never saved one) instead of always passing the default — every AI-controlled club can genuinely play differently now, not just theoretically.
- The goalkeeper's save mechanic, headers, and fouls all still fully apply in AI matches regardless of any of this, since none of them key off who's controlling a pawn. When the AI is awarded a dead-ball restart, it always takes it quickly — the quick-vs-extended choice is human-only (see "Dead-ball restarts and fouls" above), so `ai.ts` needs zero code for that either.
- **Explicitly out of scope for this pass** (not built, not started): a player-facing hire/fire UI (managers now exist and get autonomously fired/reassigned at season rollover — see "Manager system" under Career mode below — but the player can't hire/fire one directly, nor manage their own club through a manager rather than themselves), difficulty levels, and any real positional search/lookahead beyond the one-step dribble-then-kick projection above.

In `Game.tsx`, `mode: "ai"` skips the `readySides`/`handoff` dance entirely: clicking "Continue" computes the AI's moves for `"away"` synchronously and resolves immediately, so the AI's plan is never held in React state before resolution (nothing to accidentally reveal).

### Pre-game menu

`MainMenu.tsx` offers four options, all English: "Career" (see "Career mode" below — renamed from "Manage Career", now first in the list), "Local multiplayer" (hotseat, see above), "Play against AI" (human always plays `home`, AI always plays `away`), and "Team Management (testing)" (the internal `mode` value is still `"solo"`, unchanged — see below for what this mode now does). Also renders a small top-right "Fullscreen" button — see the Camera/HUD polish section's fullscreen bullet above. `App.tsx` is a three-screen state machine (`menu` / `match` / `career`) with no router; it also owns the shared fullscreen state threaded to all three.

### Career mode

Reached via `MainMenu.tsx`'s "Career" button. A full save → team → season → match loop, backed by the career tables described in the Backend section above — not a sandbox, everything here persists for real.

- **`starterLeague.ts`/`fixtures.ts`**: `POST /api/saves` auto-provisions a save's entire world in one transaction — 12 procedurally-named teams, 12 players each (`POSITION_PLAN = [GK,GK,DEF,DEF,DEF,DEF,MID,MID,MID,MID,FWD,FWD]`, randomized attributes per position archetype), a `leagues` row, `league_teams` memberships, and a full **double** round-robin fixture set. `generateRoundRobin(teamIds)` builds a single-leg schedule first (`generateSingleLegRoundRobin`, the "circle method": fixes one team, rotates the rest, `n-1` rounds for even `n`), then mirrors it — same pairings, `home`/`away` swapped, round numbers offset by the first leg's round count — for a second leg, so every team plays every opponent once at home and once away (`n=12` → 132 fixtures across 22 rounds), matching how a real league table works. **This was a real, previously-shipped bug**: the original implementation only generated the single leg (66 fixtures/11 rounds for 12 teams) — caught by the user reasoning through the tactical-profile design, not by a report of broken fixtures directly. The player is never expected to hand-build teams/leagues/fixtures — that busywork is exactly what this auto-provisioning replaces. Verified via the throwaway-script pattern (single-leg correctness for n=2..8; double-leg correctness for n=4,5,6,12 — every pair meets exactly twice with reversed home/away, no team double-booked in a round, round numbers span cleanly 1..2(n-1); starter-league content/attribute-range checks).
- **`quickSim.ts`** (backend) — an instant, non-interactive result generator for every fixture in a round the player *isn't* part of. Deliberately **not** a headless run of the real match engine: `resolve.ts` has no concept of "let it play out unattended and stop" (a match only ends when a human clicks "End Match & Record Result" — see `onCareerMatchEnd` below), so there's no clean way to auto-finish 65 other fixtures a round through the real engine. Instead: `computeTeamStrength(players)` derives an attack/defense rating from attribute averages (FWD/MID → attack, DEF + GK's `shot_stopping`/`reflexes` → defense), and `simulateScore` samples a final score from a Poisson distribution around an expected-goals figure (`BASE_EXPECTED_GOALS` × attack/defense ratio × a small home-advantage multiplier, clamped to a sane range). Verified via a throwaway script: a strong team beats a weak one ~94% of the time with a ~4:0.5 average scoreline regardless of home/away, evenly-matched teams produce realistic ~1.4-vs-1.3 average-goal scorelines.
- **Round advancement is lockstep, not per-fixture.** `POST /api/leagues/:id/simulate-round` resolves every *still-unplayed* fixture (`home_score IS NULL`) in one league+round via `quickSim`. `Career.tsx`'s match screen calls `recordResult(fixture.id, ...)` for the player's own fixture first, then `simulateRound(leagueId, fixture.round)` — which naturally skips the player's fixture (already scored) and fills in the other 5. This is the *only* path that ever writes a score, and it's the direct fix for a real bug: fixtures used to be playable/editable from a raw League Detail screen with no restriction on which fixture, so the player could launch or hand-edit *any* club's match, not just their own. That screen (`LeagueDetail.tsx`) is gone — replaced by `Calendar.tsx`, which is **read-only** (fixtures + standings, no Play button, no score-entry field anywhere). The only way to advance a season is `ClubHome`'s "Next Match" tile, which always targets the player's own team's next unplayed fixture.
- **Season rollover**: `POST /api/saves/:id/advance-season` (gated on every fixture in the current — highest-`season` — league having a recorded score) creates a **new** `leagues` row (`season + 1`) for the same teams with a fresh double round-robin, and bumps `saves.season`. The finished league's row and fixtures are never deleted or mutated — that's deliberately what makes past-season standings "history" for free, queryable via the same `GET /api/leagues/:id/standings` on the old league's id. `ClubHome` offers "Start Season N+1" in place of "Next Match" once the current league has no unplayed fixtures left. This is also where manager firings roll through — see "Manager system" below; the endpoint's response grew a `firings` array on top of the new league row.
- **Frontend screen stack** (`Career.tsx`) — same "tiny explicit state machine, no router" pattern `App.tsx` already uses, reusing the exact same `<Game>` component every other match mode uses (career's only difference: `homeTeamId`/`awayTeamId`/`humanSide`/`humanStartingPlayerIds`/`onCareerMatchEnd` props — see below). Screens, in the order a new player moves through them: **`CareerHome`** (Continue / Load Game / New Game / Return — Continue and Load Game disabled when no saves exist; Continue jumps straight to the highest-`id` save, treated as "most recent" since there's no separate last-played timestamp) → **`NewGameName`** (manager-name entry; the name doubles as the save's own `name` — there's no separate manager-name column — creating the save here is what triggers the full auto-provisioning above) → **`ChooseTeam`** (lists the 12 auto-generated teams; clicking one **navigates to a preview**, it does not commit) → **`TeamPreview`** (read-only roster view; only its "Pick this team" button actually calls `setUserTeam`) → **`ClubHome`** (the real hub every save lands on afterward — News (disabled "coming soon" tile — no market/events system exists yet), Next Match, Calendar, Team Management, Managers, Save (returns to `CareerHome` — everything already persists instantly, so this is a reassuring label, not a real save action), Exit (main menu) — there is deliberately no "Tactics" tile for the player's own team anymore, see the Tactical settings bullet below for why) → **`LineupSelect`** (see below) → the match itself. **`SavesList`** is a sibling reached from `CareerHome`'s "Load Game" — now a pure picker (save-creation moved to `NewGameName`). **`TeamManagement`** is a two-pane rebuild of the roster editor (player names left, selected player's full attribute panel right) replacing an earlier all-attributes-in-one-editable-row grid that read as an unreadable wall of tiny boxes — it now also has a second, side-arrow-paged "Formation" page (see the "Base lineup / formation" bullet below) alongside this original "Attributes" page. **`Calendar`** is the read-only fixtures+standings view described above, now also showing Top Scorers (see below).
- **The human genuinely plays home or away, matching the fixture** — a league fixture is home for one team and away for the other, and a real season alternates roughly 50/50; an earlier design always forced the human into "home" (`Career.tsx`'s match screen used to pass `fixture.home_team_id`/`away_team_id` straight through to `<Game mode="ai">`, which used to hardcode the human as "home"), fixed at the time as a stopgap for a worse bug (the human ending up controlling the AI's side — see below) but never revisited. That stopgap meant the away-kit/away-perspective side of the game never happened, and would have silently broken any future mechanic keyed off home/away (a home-advantage bonus, say). `Game.tsx` now takes an explicit `humanSide?: Side` prop (defaulting to `"home"` for every non-career caller — hotseat/solo/the plain "Play against AI" menu option never pass it) that drives *everything* keyed off "which side is the human's": initial `controllingSide`, the post-turn/post-restart resets back to it, which side `planAiTurn` controls (`aiSide`, always the other one), which team's saved tactical profile gets fetched for the AI (see the Tactical settings bullet below), the bench/substitution target gate, and corner-preset save/apply (keyed off the human's real team id, not always `teams[0]`). `Career.tsx` passes the fixture's real `home_team_id`/`away_team_id` straight through unchanged plus a computed `humanSide`, which is what fixed the underlying bug described next — and, as a bonus, means `Game.tsx`'s `homeScore`/`awayScore` already line up with the fixture's own `home_score`/`away_score` with no remapping needed on the way back into `recordResult`. Verified live: launched a fixture where the test team was the schedule's away side and confirmed via the pawns' actual `side`/`controllingSide` that the human's own roster was the side selectable and the AI genuinely controlled the other.
- **The human always controls their own team, never whichever side the schedule happened to list first** — the original bug the "always home" stopgap above was covering for, and still true today under the real fix: since a fixture's home/away designation reflects the round-robin schedule, not who's human-controlled, roughly half of a season's fixtures list the player's own team as *away* — without `humanSide` threading through every "which side can I click" check, the human would silently end up controlling their *opponent* while their own club played passively under the AI.
- **Starting lineup selection** (`LineupSelect.tsx`, between Club Home's "Next Match" and the match itself): pick exactly 6 of the player's 12-player roster to start, defaulting to the team's saved base lineup (see the Formation bullet just below) when one exists, or the same first-6-by-jersey-number selection `formation.ts` always implicitly fell back to when it doesn't (so confirming immediately is a no-op for a player who doesn't care, either way). The chosen ids are passed to `<Game humanStartingPlayerIds>`, which filters whichever roster is `humanSide`'s down to exactly those before it ever reaches `buildFormation`/`buildFormationFromLineup` — whoever isn't selected simply never becomes a pawn, benched the same way any roster surplus already is (see `formation.ts` above). This is the real prerequisite substitutions needed: before this, "who starts" was never a choice, just an accident of jersey numbering.
- **In-match substitutions**: whenever a lineup choice produced a bench (i.e. only in Career mode — hotseat/AI-from-menu/solo never pass `humanStartingPlayerIds`), `Game.tsx`'s HUD grows a "Bench (N)" toggle showing the sitting-out players; clicking one arms `subReplacement` (mirrors the existing man-mark target-picker's "arm a mode, then click the target on the pitch" shape), and the next pawn on `humanSide` clicked is who they replace. `performSubstitution` builds a fresh `Pawn` for the incoming player at the outgoing pawn's *current* position (not a formation slot — the match may be well underway) and swaps it into `match.pawns` immediately; this is a real-time action, not a planned/queued one, since a substitution happens at a stoppage in real football, not something resolved tick-by-tick. Unlimited substitutions for now — no economy/limit modeled yet, matching the "start simple" scope of this pass.
- **Base lineup / formation** (`FormationEditor.tsx`, reached via `TeamManagement.tsx`'s side arrows — see its own bullet below): a *persistent* counterpart to `LineupSelect`'s per-match, situational choice — "he sets his base team in team management and does situational adjusts on a match to match basis," in the words of the request that shaped this split. Saved to the backend's `team_lineups` table (`GET/PUT /api/teams/:id/lineup`, an opaque JSON blob of exactly 6 `{ player_id, position, x, y }` entries — `formations.ts`'s new `LineupSlot` type, a `FormationSlot` pinned to a specific player rather than just a position category) and read by both `LineupSelect` (as its default selection) and `Game.tsx`'s Career-mode kickoff (via `formation.ts`'s new `buildFormationFromLineup`, in place of the generic `buildFormation`/`FORMATION_6V6_DEFAULT` — see that function's own doc comment for how it reconciles a match-day substitute who wasn't part of the saved lineup: they inherit whichever saved slot's *player* isn't in the confirmed starting 6, position-matched via the same `assignSlots` logic every other formation path already uses, falling back to `buildFormation` entirely on any length mismatch — e.g. no lineup ever saved — rather than guessing). Coordinates are in the same home-orientation frame `FORMATION_6V6_DEFAULT` already uses (mirrored for the away side by `formation.ts`, unchanged).
  - **The editor screen itself reuses `PhaserGame`/`MatchScene` wholesale** — see "Player-driven tackling and collision rework"'s dragging bullet above for how the pawn-drag primitive was "built specifically so [it] extends cleanly later without rework"; this is that payoff realized. `pawnDragEnabled: true`, no ball/ticks, and critically **no pan/rotate/zoom controls wired up at all** (Game.tsx's own WASD/mouse-drag/wheel handlers simply aren't replicated here) — a deliberate, explicit user call ("full phaser but more limited movement, here is about setting the team, not panning around"), achieved with zero MatchScene changes since camera movement was never MatchScene's own responsibility to begin with (see "Camera, input, and HUD polish" above). The one real MatchScene addition this needed was `onPawnRightClick` on `MatchCallbacks` (optional, unused by every other mode — a pawn right-click was previously entirely unhandled by MatchScene itself, left free for the viewport's own `contextmenu` deselect/undo handler in a real match; the editor is the first consumer to actually wire it).
  - **Interactions, all toggle/swap rather than a straight add** (the roster is always exactly 6 starters + 6 bench, so bringing someone on always means benching someone else first, or swapping directly): dragging an on-pitch pawn repositions them (MatchScene's existing `onPawnDragEnd`, bounds-checked by MatchScene itself, same as the Team Management sandbox); right-clicking an on-pitch pawn (via the new callback) or a starter's row in the roster list benches them; right-clicking a bench row brings them on, into the first open slot whose saved `position` matches theirs (falling back to any open slot) — the *same* `player.position` field `assignSlots` already matches on elsewhere, not a new concept; dragging a bench row onto the pitch canvas does the same "next open slot" placement via plain HTML5 drag-and-drop (the bench list and the Phaser canvas are just two adjacent DOM elements — no cross-boundary Phaser/native-DnD plumbing needed since the canvas is a perfectly ordinary drop target); dragging a bench row onto a *specific* starter's row swaps them into that exact slot directly, rather than "next open." The roster list sorts starters first, then a "Bench" divider, matching an explicit user spec for at-a-glance clarity. Save is disabled until all 6 slots are filled (dragging one starter out and not yet replacing them is a valid, transient mid-edit state — "Open spot" placeholder rows show where). Verified live end-to-end via a throwaway save: default shape/matching on an unsaved team, right-click bench and right-click select-into-vacated-slot, drag-to-swap onto a specific starter, drag-to-fill onto the canvas, Save persisting exactly the edited slots, `LineupSelect` picking up the saved lineup as its default instead of first-6-by-jersey, and — via direct pawn-state inspection — a real match kickoff placing every non-kickoff-forward pawn at its exact saved position (the kickoff coin toss's own forward-onto-the-ball override, scoped to that one pre-existing mechanic, is the only expected deviation).
- **Goal-scorer / top-scorer tracking**: `resolve.ts`'s `GoalScorer` (see above) accumulates into `match.scorers` across the match and gets reported to `onCareerMatchEnd`, which sends the player ids (side-agnostic — a scorer's team is derived from `players.team_id` at query time, so no home/away remapping needed here unlike the score fields) to `PATCH /api/fixtures/:id`'s `scorer_player_ids`, written to `fixture_goals` inside the same transaction as the score (a re-recorded result replaces its old goal rows outright, doesn't double up). `GET /api/leagues/:id/top-scorers` aggregates and joins live, surfaced as a new "Top Scorers" table on `Calendar.tsx`. **Only ever reflects fixtures the player actually played interactively** — `quickSim.ts`'s instant results for the other 65 fixtures a round have no per-goal data to attribute, so a league's biggest rival can rack up goals in the standings that never show up here. An accepted gap, not a bug (see `quickSim.ts`'s own bullet above for why there's no clean way to run those through the real engine unattended).
- **Tactical settings — engine plumbing, no player-facing editor.** `game/tacticalProfile.ts`'s `TacticalProfile` is fully wired through `ai.ts` (see "AI opponent" above) and persisted per-team in the backend's `team_tactics` table (missing row = `DEFAULT_TACTICAL_PROFILE`, so every already-existing team needed zero migration). `Game.tsx` fetches whichever side is `aiSide`'s saved profile once teams load (`aiTacticalProfile`, sourced from `humanSide`/`aiSide` — see the humanSide bullet above, *not* always "away") and passes it into both `planAiTurn` calls — every AI-controlled club, including a career's 11 rivals, genuinely plays a different tactical identity. `careerApi.ts`'s `toTacticalProfile` does the snake_case-`TeamTacticsDTO` → camelCase-`TacticalProfile` conversion. **There used to be a player-facing `TeamTactics.tsx` screen** (a "Tactics" Club Home tile with 9 sliders) letting the player edit their *own* team's saved profile — removed once the manager system below made the gap obvious: in Career mode the human is never the AI-controlled side (`aiSide` is always the *other* team, whichever pitch side that is), so nothing ever reads the human's own `team_tactics` row, and the screen was silently editing data nobody consumed. `updateTeamTactics`/`fromTacticalProfile` (the frontend write path) were deleted along with it; the backend's `PUT /api/teams/:id/tactics` route and the underlying `upsertTeamTactics` helper stay, since the manager system below still writes through them.
- **Manager system** (`backend/src/managerGenerator.ts`, the `managers` table, `Managers.tsx`): every AI-controlled club has a manager who *owns* its tactical identity — prompted directly by a user request to make tactical settings (above) feel like something a person controls, not just a per-team config blob. The `managers` table holds a name/style/9-tactical-field row per manager; `teams.manager_id` points at whichever manager currently runs that club. **Managers own the profile, teams don't** — `team_tactics` (the table `Game.tsx`/`ai.ts` actually read, unchanged from the Tactical settings bullet above) stays the single source of truth for gameplay, and every place a manager's profile changes (hire, fire-and-replace) writes into it via the shared `upsertTeamTactics` helper, so `Game.tsx`'s fetch needed zero changes to support managers existing at all.
  - **Generation**: `generateManager()` picks one of 7 named archetypes (Balanced, High Press, Park the Bus, Counter-Attack, Wing Play, Direct, Possession — each a full base `TacticalProfile`) and jitters every field ±8% of its own `BOUNDS` range (a min/max per field baked into `managerGenerator.ts` itself, matching what the now-removed `TeamTactics.tsx` slider UI used to enforce), so managers of the same archetype are recognizable but not identical. `POST /api/saves` generates and assigns one manager to *every* one of the 12 new teams (the player's own team isn't chosen yet at save-creation time, so there's no "skip the human's team" special case here).
  - **"Employed" is derived, not stored**: a manager is employed by whichever team's `manager_id` points at them; nobody pointing at them makes them a free agent automatically — no separate status column to drift out of sync. `PATCH /api/saves/:id` (where the player actually picks their team) clears that team's `manager_id` to `NULL`, turning its starting manager into the save's first free agent — the human manages their own team directly, matching `Managers.tsx`'s own copy ("your own team has none, since you manage it yourself").
  - **Autonomous, performance-weighted firing** happens inside `advance-season`, after computing the finished league's final standings (`computeStandings`, extracted into its own reusable function for this) and before building the next season's fixtures: each team's finishing rank maps to a fire probability (bottom quartile 50%, next 35% 20%, rest 5%) via `fireAndRehireManager(teamId, saveId)`, modeling how a relegation-form manager is far more likely to get sacked than a title challenger. A fired team is refilled by preference from the save's own free-agent pool (`ORDER BY RANDOM()` over managers with no team, excluding the one just fired) — only generating a brand-new manager when no free agent exists — so a small, recognizable pool of managers actually circulates between clubs across seasons rather than every firing minting a stranger. The endpoint's response includes a `firings: ManagerFiring[]` array (`{ team_id, team_name, old_manager_name, new_manager_name, new_style }`), which `ClubHome.tsx` renders as a "Managerial changes this season" banner right after advancing.
  - **`GET /api/saves/:id/managers`** (`fetchManagers`/`ManagerDTO` in `careerApi.ts`/`careerTypes.ts`) left-joins `managers` to `teams` on `teams.manager_id`, giving every manager row a nullable `team_id`/`team_name` — `Managers.tsx` (reached from a new Club Home tile) splits this into "Club Managers" and "Free Agents" sections. **Read-only by design**: there's no hire/fire UI anywhere — a manager only ever changes hands via save creation or the autonomous firing above, matching the "start simple" scope this pass was given (a full hire/fire-at-will management layer is a natural next step, not built).
  - **Verified live end-to-end** via a throwaway save: confirmed 12 distinct managers auto-generate on creation; confirmed picking a team clears exactly that team's manager to a free agent; simulated a full season (all 132 fixtures) and called `advance-season`, observing 3 real firings including a manager correctly reused from the free-agent pool and a multi-team chain (one manager's old club rehiring the manager freed by a *different* firing in the same rollover); confirmed the fired team's `team_tactics` row exactly matches its new manager's stored profile; confirmed the browser UI (ClubHome's "Managers" tile, the Club Managers/Free Agents split, team pick clearing a manager) end-to-end. Throwaway save deleted after verification.
- **`career.css`'s dark-mode text-visibility gotcha** — worth understanding before adding any new career screen. `index.css`'s `:root` declares `color-scheme: light dark`, and under `prefers-color-scheme: dark` its `--bg`/`--text` vars flip to near-black/near-white. Three *different* things broke because of this, not one: (1) plain inherited text color — fixed by pinning `.career-page { background: #fff; color: #1a1a1a; }`, since nothing in this subtree was written to be dark-mode-aware; (2) `h1`/`h2` — `index.css` gives them their own **direct** `color: var(--text-h)` rule (a *separate* variable from `--text`), which as a same-element rule wins over inheriting `.career-page`'s pinned color regardless of specificity tricks — fixed with an explicit `.career-page h1, .career-page h2 { color: #1a1a1a; }` override; (3) **native form controls** (`input`/`select`/`button`) — `color-scheme: light dark` lets the browser render their background/text using OS dark-mode widget defaults for any property the author didn't set explicitly, which is why unstyled `<input>`s were rendering as solid black boxes and plain `<button>`s (no explicit `color`) were rendering invisible white-on-white text — fixed with `color-scheme: light;` on `.career-page` (pins every native control in the subtree to light rendering) plus a `:where(.career-page) button { color: #1a1a1a; }` fallback for buttons with no other color rule. The `:where()` wrapper is deliberate: it keeps that fallback at effectively zero specificity so it can never fight the real, intentional colors on `.career-btn-primary`/`.career-home-button`/etc. If you add a new career screen with its own unstyled `<input>`/`<button>`, it inherits these fixes automatically via `.career-page`; don't hardcode colors that only work in light mode elsewhere in this subtree.
- **Explicitly out of scope for now**: real offside rules (deferred to a future 11v11 phase, matching the same reasoning already noted under "Dead-ball restarts and fouls" — offside has no real analog at 6v6 with a 2-defender back line); free-kick position presets (see the corner-preset bullet under "Dead-ball restarts and fouls" for why corners generalize to a flat preset and fouls don't); mid-match substitution limits/economy (unlimited for now — see the substitutions bullet above); top-scorer stats for quick-simmed (non-user-played) fixtures (no per-goal data exists for those — see the goal-scorer bullet above); a player-facing hire/fire UI for managers (autonomous firing exists — see "Manager system" above — but the player has no direct control over it); newgens/aging/retirement/form (still the long-term scope named in "What this is" above); a News/market events system; a card/suspension system (same gap already noted under "Dead-ball restarts and fouls" — not career-specific).

### Team Management sandbox (`mode === "solo"`)

What used to be a bare "away side never gets a plan" practice mode is now also the first version of a future, much larger Team Management window — a sandbox for creating, placing, deleting, and editing pawns to support a deeper upcoming balancing pass, built to grow incrementally rather than as a one-shot feature. Explicitly **session-only by design, not by backend limitation**: everything here lives in `Game.tsx`'s React state and is lost on refresh/exit. Real write endpoints (`POST`/`PATCH`/`DELETE` for teams/players) do now exist in `backend/src/index.ts` — Career mode's `TeamManagement.tsx` (see "Career mode" above) uses them for real, persistent roster edits — but this standalone sandbox deliberately doesn't call them; it's meant as a disposable, hand-controlled testing space, not a second way to edit a career save's roster. Don't conflate the two "Team Management" screens — this is the older, unrelated one.

- **Adding a pawn** is a two-step, click-to-place flow mirroring the existing man-mark-target-picker pattern: `handleAddPlayer(side)` arms `placingPawnSide`, showing a `hud-banner` hint ("Click the pitch to place the new player"); the *next* field click (checked at the very top of `handleFieldClick`, before any of the normal move/kick logic) builds a fresh `Pawn`/`PlayerDTO` at that point and appends it. Clicking an *existing* pawn while placing redirects into the same field-click path (same reasoning as kick-mode's own pawn-click redirect) rather than selecting that pawn instead. Synthetic ids start at `100000` (`nextCustomPlayerId`, a ref-held counter) specifically so they can never collide with a real id fetched from the backend. New pawns get generic mid-range defaults (all attributes 50, position `MID`, name "New Player") — the whole point is to immediately retune them via the edit panel.
- **The Team Management panel** (`teamManagementOpen`, toggled from a `mode === "solo"`-only button next to Fullscreen/Continue) is a new `hud-middle-row` inserted between the HUD's existing top and bottom rows — the fixed five-zone HUD layout gained a middle slot specifically for this, only ever rendered in this one mode. Shows both sides' rosters (name/position/jersey#, a delete button per row, click-to-select) side by side, an away-side "AI" checkbox, and — whenever a pawn is selected while the panel is open — an edit section (name, jersey number, a position `<select>`, and all seven attributes as plain number inputs) wired through `handleEditPlayerField`, which always spreads a **new** `player` object rather than mutating the fetched `PlayerDTO` in place.
- **Roster-list selection deliberately bypasses `handlePawnClick`'s `pawn.side !== match.controllingSide` gate** (`handleSelectFromRoster`) — unlike normal play, this sandbox lets you select, edit, or even manually plan a move for *either* side's pawns, not just the turn's controlling side. This is a genuine, if incidental, bonus: with the AI toggle off, you can hand-control both sides for testing; turning AI on simply overwrites away's plan wholesale at Continue time regardless of anything planned here by hand, same as `mode === "ai"` already does.
- **The AI toggle** (`awayAiEnabled`, default off, matching solo's original meaning) is read live by `handleReady`'s existing `mode === "solo"` branch — on, it calls `planAiTurn` exactly like `mode === "ai"` does; off, away simply never gets a `plannedSteps` chain, same as before this sandbox existed.
- **A goal no longer rebuilds the roster** in this mode: `resolveWithPawns`'s goal-handling block skips the `kickoffFormation` call when `mode === "solo"` (leaving `pawns` exactly as the player built it) and only re-centers the ball. Everywhere else, scoring still resets both sides to the standard 6-pawn kickoff formation.
- **No 6-per-side ceiling anywhere in the engine** — verified before building this: `formation.ts`'s `assignSlots` is slot-count-driven with no hardcoded count, `resolve.ts`/`contest.ts`/`ai.ts` all scale off actual roster size, and `MatchScene.ts`'s `updatePawns` already adds/removes pawn visuals by id with no fixed-count assumption. Added pawns go straight onto the pitch alongside the starting 6 — there's no bench/roster-vs-on-field distinction in this first version.
- **Known limitation, not solved here**: `resolve.ts` picks the *first* GK it finds per side for save/penalty logic — a second GK on one side won't crash anything, but only the first one found is ever treated as the keeper.
- **Dragging an existing pawn to any position** (`pawnDragEnabled` on `MatchSyncState`, `mode === "solo" && !placingPawnSide` — disabled while a *new* pawn's placement is armed, so a press on an existing pawn is never ambiguous between "move this one" and "place the new one here") is the first real drag gesture in a codebase that's otherwise been entirely click-based, and it has to coexist with left-click-drag camera panning (see "Camera, input, and HUD polish" above) — *any* left-button drag on the canvas would otherwise pan the camera regardless of what's under the cursor. `MatchScene.ts`'s pawn `pointerdown` handler fires a new `onPawnPointerDown` callback synchronously, *before* `Game.tsx`'s own mousedown handler runs (the same canvas-fires-before-React-div bubble-phase ordering the click-vs-drag-threshold system already depends on) — `Game.tsx` sets `draggingPawnRef` from it and skips starting a camera pan for that gesture. Live drag visuals stay entirely inside `MatchScene` (a scene-wide `pointermove` directly repositions the dragged pawn's container to follow the cursor, same "no React round-trip per move" approach the kick-aim preview already uses) — only the drop (`pointerup`, past `CLICK_DRAG_THRESHOLD`) calls back into `Game.tsx`'s `handlePawnDragEnd`, which sets that pawn's `pos` and clears its `plannedSteps` (a queued chain computed from the old position doesn't mean anything once the pawn's been teleported). `MatchScene` owns its own bounds check (`isInBounds`, a small deliberate duplicate of `Game.tsx`'s own — the same "defensive backstop" shape `resolve.ts`'s `clampStepsToBudget` already uses) and snaps the sprite back itself on a rejected drop, since nothing in `Game.tsx`'s state would otherwise change to trigger a fix. Built specifically so the same primitive extends cleanly later without rework: in-match substitutions were the first payoff (built later, see "In-match substitutions" under Career mode below — a simpler click-based swap, not actually `onPawnDragEnd`-driven). **The formation/tactic editor predicted here was the second, and did reuse this exact primitive as-is**: Career mode's Team Management "Formation" page (see its own bullet under Career mode below) is `PhaserGame`/`MatchScene` reused wholesale with `pawnDragEnabled: true`, no ball/ticks, and no pan/rotate/zoom controls wired up — reading the *current* on-pitch positions dragging already produces and serializing them was genuinely all that page needed from MatchScene's side; the only actual MatchScene change that page required was a new, unrelated `onPawnRightClick` callback (see below) for its own bench/select gesture.
